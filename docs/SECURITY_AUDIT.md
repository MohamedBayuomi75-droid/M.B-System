## 3. (ب) نسخة الويب — الثغرات والنواقص قبل الإنتاج

| # | البند | الخطورة | المقترح |
|---|---|---|---|
| W1 | **XSS مخزّن** (S7): مستخدم يكتب HTML في اسم/ملاحظة فيتنفذ عند مستخدم تاني (ومنه أدمن) | 🔴 | مراجعة كل نقط `innerHTML` + اختبار payload على كل الحقول + CSP |
| W2 | **مفيش CSP ولا headers أمان** (HSTS, X-Content-Type-Options, frame-ancestors) | 🔴 | CSP report-only ثم إنفاذ (الـ 161 `onclick` بيصعّبوها — محتاجة خطة) |
| W3 | **مفيش HTTPS/reverse proxy** لسه | 🔴 | Nginx/Caddy + شهادة (راجع التعارض في Gap Analysis §4) |
| W4 | **مفيش نسخ احتياطي ولا اختبار استعادة** | 🔴 | المرحلة 9 في الخطة |
| W5 | رفع الملفات **مش منفّذ** (فحص النوع/الحجم/المحتوى) | 🟠 | مع موديول المرفقات |
| W6 | مفيش 2FA للأدمن | 🟠 | TOTP |
| W7 | CSRF: الحماية الحالية = Bearer في الهيدر للـ API + `SameSite=Lax` للكوكي؛ مفيش فحص `Origin` على `/api/auth/refresh` | 🟡 | فحص Origin |
| W8 | الحقول المخصصة (`custom{}`, `extraFields[]`) مش محمية لو اتحط فيها راتب | 🟠 | تعريف حساسية للحقل المخصص |
| W9 | `audit_log` و`changes`: الـ API مابيسمحش بتعديلهم، لكن **مفيش حماية على مستوى القاعدة** (مستخدم القاعدة يقدر يعدّل)، ومفيش سياسة احتفاظ | 🟠 | صلاحيات DB منفصلة / trigger يمنع UPDATE/DELETE + سياسة |
| W10 | عدّاد الـ rate limit في الذاكرة (instance واحد) | 🟡 | كافي لسيرفر واحد |
| W11 | مكتبة `xlsx` القديمة بتتحمّل في المتصفح (S8) | 🟠 | تحديث النسخة |
| W12 | Swagger مفتوح لو `SWAGGER_ENABLED=true` | 🟡 | مقفول افتراضيًا في الإنتاج ✅ — يفضل كده |
| W13 | حد الدخول لكل IP+مستخدم: مستخدمين ورا نفس الـ NAT بنفس الحساب ممكن يتقفلوا | 🟡 | سياسة «حساب لكل شخص» |

## 4. الخلاصة

- الديسكتوب آمن **كبرنامج جهاز واحد**؛ وضع الشبكة القديم (S5) ماينفعش يتعرّض لشبكة مش موثوقة.
- نسخة الويب: **المصادقة والصلاحيات وعزل البيانات على السيرفر معمولين ومختبَرين**، وده أهم متطلب في الخطة (§6: «عدم الاعتماد على حماية الواجهة»).
- **4 بنود حرجة تمنع الإنتاج**: XSS (W1)، CSP/headers (W2)، HTTPS (W3)، النسخ الاحتياطي المختبَر (W4).
