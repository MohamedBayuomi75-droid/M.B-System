## 2. نطاق 6.1 في الخطوة دي (دورة النقل من 1 لـ 9 ماعدا 7)
| خطوة | ما سيُنفَّذ |
|---|---|
| 1–2 | حصر وظائف شاشتي «الموردين» و«العملاء»، وتوثيق قواعدها بالملف والسطر (`docs/modules/PARTIES_MODULE.md`) |
| 3 | الاختبارات المرجعية الحالية للواجهة القديمة بتفضل حَكَم: 62/62 |
| 4 | تصميم جدولي `suppliers` و`customers` العلائقيين (NUMERIC(18,4)). **الجداول فاضية** |
| 5 | Resource API `/api/v1/suppliers` و`/api/v1/customers` (قراءة + إضافة + تعديل) بنفس القواعد على الخادم. الكتابة **بتمر بنفس طبقة السجلات** اللي الواجهة القديمة بتكتب فيها، يعني: مفيش نسختين قابلتين للكتابة، والبث اللحظي والتدقيق والتعارض شغالين زي ما هم |
| 6 | الـ Adapter مش محتاج تغيير دلوقتي، لأن المصدر لسه واحد (`records`). تحويله للجداول بيحصل مع الترحيل |
| 7 | **مش هيتنفّذ:** خطة ترحيل dry-run بس (أعداد وتعارضات وفروق تقريب). الترحيل الفعلي محتاج موافقتك ونسخة احتياطية مستعادة |
| 8 | شاشات Angular (تجريبي) للموردين والعملاء: بحث وإضافة وتعديل. الشاشات القديمة بتفضل الأساسية |
| 9 | اختبارات تكافؤ: اللي يتكتب من API الجديد يظهر في الواجهة القديمة بنفس الشكل، والعكس |

**مش في النطاق:**
- أرصدة الموردين وكشوف الحساب (بتتحسب من الفواتير والدفعات، ومكانها 6.3/6.4).
- الحذف وسلة المهملات (مرتبطين بالأرشيف، وبيفضلوا في الواجهة القديمة).
- قلب التوجيه (الخطوة 11).

## 4. المخاطر
| الخطر | المعالجة |
|---|---|
| الكتابة من شاشتين على نفس السجل | نفس طبقة السجلات بـ `rev`. التعارض بيرجّع 409 بالنسخة الحالية |
| فروق شكل البيانات بين الـ API والواجهة القديمة | الـ API بيكتب **نفس الحقول ونفس الأنواع** اللي الواجهة القديمة بتكتبها، واختبار التكافؤ بيتأكد |
| الواجهة القديمة بتقرّب رصيد العميل الافتتاحي لخانتين (`toInt` ← `round2` — `renderer/core/helpers.js:21`) | الـ API بيقبل خانتين بس للعميل مؤقتًا، عشان أي تعديل من الشاشة القديمة مايغيّرش القيمة. القيد ده بيتشال مع نقل الشاشة. ومسجّل كبند للمراجعة |

**الرجوع:** migration جديدة ليها `down`، والإضافات في موديول منفصل، والشاشات القديمة من غير تغيير.
