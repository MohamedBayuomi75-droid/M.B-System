أنت تعمل كمهندس حلول ERP ومهندس برمجيات Senior.

مهمتك الحالية هي فحص المشروع بالكامل، والتحقق من نتائج التدقيق السابق، وإعداد وثائق المعمارية والقرارات وخطط التنفيذ.

## 2. قرارات المستخدم النهائية

هذه القرارات معتمدة ولا يجوز تغييرها من تلقاء نفسك:

### A. Access: INTERNAL
- النظام يعمل داخل شبكة الشركة فقط في المرحلة الأولى.
- لا يوجد نشر عام على الإنترنت.
- لا تكشف قاعدة البيانات أو الخدمات الحساسة خارجيًا.
- يمكن دراسة VPN مستقبلًا بقرار مستقل.

### B. Accounting: GRADUAL
- تصميم محاسبة قيد مزدوج كاملة من البداية.
- التنفيذ والتفعيل تدريجيًا.
- كل قيد مرحّل يجب أن يكون متوازنًا ($Debit = Credit$).
- لا تسمح بتعديل أو حذف القيود المرحلة مباشرة.
- التصحيح يتم بقيود عكسية أو تسويات موثقة.

### C. Approvals: LEVELS
- اعتماد الفواتير والمدفوعات بمستويات متعددة.
- مسار الاعتماد يعتمد على نوع المستند وقيمته.
- يجب أن يكون محرك الاعتمادات قابلًا للتهيئة.
- **لا تخترع** حدودًا مالية أو مسميات وظائف أو عدد مستويات.
- اترك مصفوفة الاعتماد كقرار تجاري مطلوب من إدارة الشركة.

### D. Architecture
- **الاتجاه المستهدف (Frontend):** Angular + Angular Material.
- **الخادم (Backend):** NestJS.
- **قاعدة البيانات (Database):** PostgreSQL.
- **الخادم العكسي (Reverse Proxy):** Nginx.
- **النمط المعماري:** Modular Monolith كبداية.
- الواجهة الحالية وAngular تعملان بالتوازي عند الحاجة.
- Backend واحد وقاعدة بيانات تشغيلية واحدة.
- المرفقات تُخزن داخل PostgreSQL وفق القرار الحالي.

## 3. الوثائق المطلوب إنشاؤها

أنشئ داخل مجلد `docs/` الملفات الخمسة التالية:

### 1. `docs/TARGET_ARCHITECTURE.md`
تتضمن:
- الوضع الحالي المثبت.
- الوضع المستهدف.
- رسم معماري (Architecture Diagram).
- طبقات النظام ومسؤولياتها.
- حدود الموديولات (Module Boundaries).
- Backend وDatabase الموحدين.
- الانتقال التدريجي إلى Angular.
- الأمن والصلاحيات.
- المرفقات.
- النسخ الاحتياطي والاستعادة.
- النشر الداخلي.
- الاختبارات والمراقبة.
- المخاطر والقرارات المفتوحة.

### 2. `docs/ARCHITECTURE_DECISIONS.md`
اكتب سجل القرارات المعمارية (ADR). لكل قرار، وضح:
- رقم القرار.
- العنوان.
- الحالة: `Accepted` / `Proposed` / `Needs Decision`.
- السياق.
- القرار.
- البدائل.
- النتائج الإيجابية والسلبية.
- الأدلة من الكود.
- متى يمكن إعادة النظر فيه.

**سجل القرارات المعتمدة صراحة:**
- Internal Access.
- Gradual Double-Entry Accounting.
- Multi-Level Approvals.
- Angular Migration Gradually.
- Shared Backend.
- Single Operational Database.
- Attachments in PostgreSQL.

### 3. `docs/APPROVAL_WORKFLOW_DESIGN.md`
صمم محرك اعتماد عام قابلًا للتهيئة. يجب أن يدعم:
- أنواع المستندات.
- حدود القيمة من وإلى.
- عدد مستويات الاعتماد.
- الأدوار والمستخدمين.
- ترتيب المستويات.
- الاعتماد المتتابع أو المتوازي عند الحاجة.
- التفويض المؤقت.
- الرفض والإرجاع وإعادة الإرسال.
- سجل انتقال الحالات.
- منع اعتماد مقدم الطلب لمستنده افتراضيًا.
- منع التعديل غير المصرح أثناء الاعتماد.
- الفصل بين `Approved` و `Posted`.
- إعادة تقييم الاعتماد عند تغيير القيمة أو البيانات الجوهرية.
- منع التلاعب بالحالات من خلال API.

> **قيد صارم:** لا تخترع حدودًا مالية أو مسميات وظيفية أو عددًا ثابتًا للمستويات. ضع هذه القيم كإعدادات غير محددة، واكتب أنها تحتاج قرار الإدارة. أضف حالات اختبار للنجاح والفشل والتزامن وتعارض الاعتمادات.

### 4. `docs/ACCOUNTING_ROADMAP.md`
صمم خطة المحاسبة المزدوجة. يجب أن تشمل:
- Chart of Accounts (دليل الحسابات).
- Fiscal Periods (الفترات المالية).
- Journal Entries (القيود اليومية).
- Journal Lines (سطور القيود).
- Debit / Credit balancing (توازن المدين والدائن).
- General Ledger (الأستاذ العام).
- Trial Balance (ميزان المراجعة).
- Cash & Banks (النقدية والبنوك).
- Receipts & Payments (المقبوضات والمدفوعات).
- Customers & Suppliers (العملاء والموردون).
- Invoices (الفواتير).
- Project Costing (تكاليف المشاريع).
- Cost Centers (مراكز التكلفة).
- Taxes & Withholding (الضرائب والاستقطاعات).
- Reversals & Adjustments (القيود العكسية والتسويات).
- Period Closing (إقفال الفترات).
- Opening Balances (الأرصدة الافتتاحية).
- Data Migration & Reconciliation (ترحيل البيانات والمطابقة).

> **قيد صارم:** قسّم التنفيذ إلى مراحل تدريجية. لا تضع نسب ضرائب أو سياسات محاسبية على أنها معتمدة دون دليل أو موافقة.

### 5. `docs/OPEN_BUSINESS_DECISIONS.md`

- مصفوفة الاعتمادات.
- دليل الحسابات.
- الضرائب والاستقطاعات.
- سياسة التقريب.
- العملات.
- مراكز التكلفة.
- المشتريات.
- السلامة والمخاطر.
- الجودة والاستلام.
- المعدات.
- العمالة والمستحقات.
- مواصفات الخادم.
- عدد المستخدمين.
- حجم المرفقات.
- RPO / RTO.
- مدة الاحتفاظ بالنسخ.
- التفويض والاستثناءات.

**لكل سؤال وضح:**
- سبب الحاجة إليه.
- ما الذي يتوقف عليه.
- صاحب القرار المقترح.
- ما إذا كان يمنع التنفيذ أو يمكن تأجيله.

## 4. التدقيق الفني المطلوب

افحص الكود الحالي فعليًا، مع ذكر مسارات الملفات والأسطر أو المراجع والاختبارات. تحقق من:

1. المعادلات المالية والضرائب والخصومات والاستقطاعات.
2. إنشاء الفواتير والمقبوضات والمدفوعات وتعديلها وحذفها.
3. التحقق من أرصدة المخزون من جهة Backend.
4. منع تكرار أرقام المستندات عند الطلبات المتزامنة.
5. ربط الموظفين والعمال والمشروعات باستخدام IDs ثابتة.
6. فرض الصلاحيات على الخادم.
7. اكتمال Audit Log وحماية سجلاته.
8. حفظ المرفقات وصلاحيات تنزيلها.
9. النسخ الاحتياطي والاستعادة الفعلية.
10. تكرار منطق الأعمال بين الواجهة والخدمات.
11. الاختبارات التشغيلية لكل صفحة.
12. تغطية المعادلات المالية باختبارات مباشرة.

**صنف كل نتيجة إلى:**
- `VERIFIED`: تحققت بنفسك.
- `REPORTED`: مذكورة في تقرير سابق ولم تتحقق منها الآن.
- `ASSUMPTION`: استنتاج يحتاج تحققًا.

*(لا تعتبر وجود صفحة أو زر دليلًا على اكتمال الوظيفة).*

## 5. ضوابط صارمة في هذه المرحلة

### ممنوع:
- تعديل كود التطبيق.
- تعديل قاعدة البيانات.
- تشغيل Migrations.
- حذف أو إعادة تسمية ملفات قائمة.
- تعديل بيانات المستخدمين.
- تثبيت أو تحديث Dependencies.
- تغيير إعدادات الشبكة أو Firewall أو Docker أو Nginx.
- تشغيل أوامر `DROP` أو `TRUNCATE` أو `RESET` أو أي أوامر مدمرة.
- تشغيل اختبارات قد تغير بيانات الإنتاج.
- بدء تنفيذ Angular أو نقل الموديولات.

### المسموح:
- القراءة والفحص.
- اختبارات آمنة لا تغير البيانات (Read-only / Unit tests).
- إنشاء وتحديث ملفات Markdown المطلوبة فقط.

## 6. طريقة التنفيذ

1. افحص حالة Git والـ Branch الحالي دون تغييره.
2. افحص ملفات المشروع ومجلداته.
3. اقرأ تقارير التدقيق السابقة.
4. تحقق من صحة نتائجها الحالية.
5. افحص المسارات المالية والمخزنية والأمنية.
6. راجع تصميم قاعدة البيانات والعلاقات.
7. اكتب الوثائق الخمس.
8. راجع توافق الوثائق مع قرارات المستخدم.
9. راجع `git diff` و `git status`.
10. تأكد أن التغييرات تقتصر على ملفات Markdown المطلوبة.

> **تنبيه:** لا تنفذ `git commit` دون طلب.

---

## 7. التقرير النهائي

اكتب تقريرًا شاملًا بالعربية في نهاية عملك يشمل:
- الملفات التي أنشأتها.
- ما تم التحقق منه فعليًا.
- ما لم يتم التحقق منه.
- المخاطر ذات الأولوية.
- الاختبارات التي تم تشغيلها ونتائجها.
- القرارات التجارية المفتوحة.
- الخطوة التالية المقترحة.

**أكد بوضوح في التقرير أن كود التطبيق وقاعدة البيانات لم يتم تعديلهما.**

---

## 8. نقطة التوقف الإلزامية

بعد إعداد الوثائق والتدقيق:
1. **توقف ولا تبدأ التنفيذ.**
2. اعرض النتائج وانتظر موافقة المستخدم الصريحة على المرحلة التالية.
3. لا تنفذ أي Migration أو تعديل كود أو تغيير قاعدة بيانات قبل الحصول على الموافقة.

**ابدأ الآن بالتدقيق والتوثيق فقط.**
