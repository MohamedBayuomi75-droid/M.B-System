# المعمارية المستهدفة لنظام ERP لشركة مقاولات عامة

- **الإصدار:** 1.0
- **الحالة:** قرارات معمارية معتمدة مبدئيًا
- **نطاق المرحلة الأولى:** تشغيل داخلي داخل شبكة الشركة.

---

## 1. الهدف

تطوير نظام ERP متكامل لشركة مقاولات عامة، مع الحفاظ على جميع وظائف البرنامج الحالي وبياناته، وتحويله تدريجيًا إلى بنية قابلة للتوسع وآمنة ومتعددة المستخدمين.

> **قاعدة أساسية:** يجب ألا يؤدي التطوير إلى فقد أي وظيفة موجودة أو استبدال وظيفة حقيقية بواجهة شكلية.

---

## 2. القرارات المعمارية المعتمدة

### القرار الأول: الوصول إلى النظام
- **القيمة المعتمدة:** `INTERNAL`
- النظام متاح من داخل شبكة الشركة فقط في المرحلة الأولى.
- لا يتم نشر النظام للعامة على الإنترنت.
- لا يتم فتح PostgreSQL أو Backend مباشرة على الإنترنت.
- يتم استخدام HTTPS داخليًا.
- يتم التحكم في الوصول من خلال المستخدمين والأدوار والصلاحيات.
- يمكن دراسة VPN مستقبلًا بقرار منفصل.

### القرار الثاني: المحاسبة
- **القيمة المعتمدة:** `GRADUAL`
- تصميم النظام من البداية لدعم محاسبة قيد مزدوج كاملة.
- لا يتم اختزال المحاسبة إلى أرصدة منفصلة أو حسابات غير مترابطة.
- يتم تنفيذ المحاسبة وتفعيل وظائفها تدريجيًا.
- يجب أن تكون كل مرحلة متوافقة مع الهيكل المحاسبي النهائي.
- كل قيد مرحّل يجب أن يحقق توازن المدين والدائن ($\text{Debit} = \text{Credit}$).
- لا يسمح بتعديل أو حذف القيد المرحّل مباشرة؛ التصحيح يكون بقيد عكسي أو تسوية موثقة.

**المراحل المقترحة:**
1. دليل الحسابات والفترات المالية والقيود اليومية.
2. ربط الخزينة والبنوك والمقبوضات والمدفوعات.
3. ربط العملاء والموردين والفواتير.
4. ربط المشروعات والتكاليف ومراكز التكلفة.
5. التقارير المالية ودفتر الأستاذ وميزان المراجعة.
6. الأرصدة الافتتاحية والتحويل المحاسبي بعد المطابقة.

### القرار الثالث: اعتماد الفواتير والدفعات
- **القيمة المعتمدة:** `LEVELS`
- يجب بناء محرك اعتماد متعدد المستويات وقابل للتهيئة.

**يعتمد مسار الموافقة على:**
- نوع المستند.
- قيمة المستند.
- عدد مستويات الاعتماد المطلوبة.
- الدور أو المستخدم المخول في كل مستوى.
- ترتيب الاعتماد.
- التفويض المؤقت عند الحاجة.

**لا يتم افتراض:**
- حدود مالية معينة.
- أسماء وظائف أو مسميات إدارية.
- عدد ثابت من مستويات الاعتماد.
- صلاحية مقدم الطلب لاعتماد مستنده.

> تظل هذه التفاصيل إعدادات مفتوحة إلى حين اعتماد مصفوفة الصلاحيات من إدارة الشركة.

## 6. ضوابط المحاسبة

- استخدام PostgreSQL `NUMERIC` للقيم المالية، وليس `FLOAT`.
- توحيد قواعد التقريب داخل Backend.
- عدم وضع المعادلات المالية داخل مكونات الواجهة.
- حفظ مصدر كل قيد محاسبي.
- منع تكرار أرقام المستندات حتى مع الطلبات المتزامنة.
- استخدام معاملات قاعدة البيانات (Database Transactions) للعمليات المالية المترابطة.
- توثيق الضرائب والاستقطاعات والخصومات قبل اعتماد قواعدها.
- اختبار كل معادلة مالية بصورة مستقلة.

## 7. تصميم الاعتمادات

**الحالات العامة المقترحة:**
$$\text{Draft} \rightarrow \text{Submitted} \rightarrow \text{Under Review} \rightarrow \text{Approved} \rightarrow \text{Posted}$$

**حالات أخرى ممكنة:**
- `Rejected`
- `Returned`
- `Cancelled`
- `Reversed`

> **قيد صارم:** يجب الفصل بين `Approved` و `Posted`.

**قواعد إلزامية:**
- الاعتماد يتم في Backend.
- لا يكفي إخفاء الأزرار من الواجهة.
- كل قرار اعتماد يسجل المستخدم والتوقيت والمستوى والقرار والملاحظات.
- منع تعديل البيانات الجوهرية أثناء الاعتماد إلا وفق إجراء معتمد.
- إعادة تقييم مسار الاعتماد إذا تغيرت قيمة المستند أو بياناته الجوهرية.
- بعد الترحيل لا يسمح بالحذف أو التعديل المباشر.
- منع مقدم الطلب من اعتماد مستنده افتراضيًا.

## 8. الأمن

- الوصول داخلي فقط.
- HTTPS داخلي.
- Firewall.
- عدم كشف PostgreSQL لأجهزة المستخدمين أو الإنترنت.
- RBAC على مستوى الموديول والصفحة والفعل ونطاق البيانات.
- فحص الصلاحيات في Backend لكل Endpoint.
- حماية XSS و SQL Injection و CSRF وفق نمط المصادقة.
- إدارة آمنة للجلسات وكلمات المرور والأسرار.
- CSP وسياسات أمن المتصفح.
- Audit Log للعمليات الحساسة.

## 9. المرفقات والأرشيف

- **القرار الحالي:** تخزين المرفقات داخل PostgreSQL.

**يجب:**
- تحديد آلية التخزين المناسبة.
- تسجيل اسم الملف ونوعه وحجمه وبصمته (Hash/Checksum).
- التحقق من الملفات قبل الحفظ.
- فرض صلاحيات العرض والتنزيل من Backend.
- تضمين المرفقات في النسخ الاحتياطية.
- اختبار استعادة الملفات فعليًا.
- ربط الملفات بالمشروعات والعقود والمستندات ذات الصلة.

## 10. النسخ الاحتياطي والاستعادة

**يجب أن تشمل النسخ:**
- قاعدة البيانات.
- المرفقات.
- الإعدادات اللازمة للتشغيل.
- المعلومات اللازمة لاستعادة النظام بأمان.

**ويجب:**
- تشفير النسخ.
- حفظ نسخة منفصلة عن جهاز الخادم.
- تسجيل نجاح وفشل النسخ.
- اختبار الاستعادة دوريًا.
- مقارنة أعداد السجلات والمرفقات بعد الاستعادة.
- تحديد RPO و RTO بعد اعتماد الإدارة.

## 13. معيار قبول النظام

لا يعتبر أي موديول مكتملًا لمجرد ظهور شاشاته.

**يجب اختبار:**
- كل الوظائف والأزرار.
- الصلاحيات.
- العمليات الفعلية.
- المعادلات.
- حالات الخطأ.
- التكامل مع الموديولات الأخرى.
- حفظ البيانات واسترجاعها.
- عدم فقد أي وظيفة من النظام السابق.

> **القاعدة الأساسية:** لا حذف، لا اختصار، لا استبدال شكلي، ولا Migration خطرة دون مراجعة وموافقة.
