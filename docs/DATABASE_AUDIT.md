## 3. (ب) PostgreSQL الحالي — الطبقة 1

**الجداول (10)** — من `server/src/migrations/` (`InitLayer1`, `RolesFk`, `ChangesRealtime`):

| الجدول | المفتاح والقيود | الغرض |
|---|---|---|
| `users` | `id uuid` PK · اسم المستخدم فريد بدون حساسية للحالة · CHECK على خوارزمية كلمة المرور وعلى وجود salt للـ scrypt · FK `role → roles.key` | **مفصول عن الموظفين** ✅ |
| `sessions` | FK `user_id` (CASCADE) · `token_hash` فريد | refresh tokens (hash بس) |
| `roles`, `user_permissions` | PK `key` · PK `(user_id, page)` + FK | قوالب الأدوار وتخصيص المستخدم |
| `records` | PK `(collection, id)` · CHECK `rev > 0` · فهرس `(collection, project_id)` · فهرس جزئي للسجلات الحية | كل سجلات الـ 53 مجموعة كـ JSONB |
| `docs` | PK `key` · CHECK `rev > 0` | الإعدادات والقوائم |
| `changes` | `seq bigserial` PK · CHECK على `op` · فهرس `(collection, record_id, rev)` · trigger `NOTIFY` | سجل تغييرات متسلسل: مين، إمتى، أنهي حقول، القيم الجديدة |
| `audit_log` | `id bigserial` · فهارس بالوقت/المستخدم/الكيان | أحداث الأمان والمستخدمين + سجل الواجهة |
| `attachments` | `id uuid` · `storage_key` فريد · CHECK الحجم | **معرّف ومش مستخدم لسه** |
| `schema_meta` | PK `key` | نسخة الـ schema القديم |

**متحقق منه باختبارات** (`server/test/schema.e2e-spec.ts`, `data.e2e-spec.ts`, `load.e2e-spec.ts`): الترحيلات من الصفر، مطابقة الكيانات للجداول (من غير drift)، التراجع الكامل وإعادة التطبيق، القيود، transaction لكل طلب حفظ، soft delete، تسلسل الكتابة، 50 مستخدم متزامن من غير فقد تعديل.

## 4. تقييم: الطبقة 1 (JSONB) حل انتقالي مقصود مش التصميم النهائي

`UNIFIED-WEB-PLAN.md §2.2` اختار JSONB عشان الواجهة القديمة تشتغل فوق السيرفر **من غير إعادة كتابة ومن غير فقد أي وظيفة**، مع «ترقية» كل موديول لجداول علائقية وقت نقله لـ Angular، والطبقة 1 تفضل adapter فوقها. ده متوافق مع أولوية الخطة الرئيسية الأولى (الحفاظ على الوظائف)، لكنه **مش بيحقق** متطلبات §5 و§11 (FK، NUMERIC، قيود مالية) غير بعد الترقية. يعني تصميم الجداول العلائقية لكل موديول **لسه ماتعملش** وهو المرحلة 3 في الخطة الرئيسية.

## 5. مخاطر الترحيل (لما ييجي وقته — مفيش ترحيل اتنفذ)

| الخطر | التعامل المقترح |
|---|---|
| فقد/تغيير أرقام وقت النقل | dry-run بتقرير أعداد ومجاميع قبل/بعد + مقارنة إعادة بناء `DATA` بالأصل (تجربة النهارده: البيانات الحقيقية اترفعت لقاعدة اختبار ورجعت بنفس الأعداد ومن غير تغييرات معلّقة) |
| float → NUMERIC | تقريب موثّق لكل حقل + تقرير بأي سجل مجموعه اتغيّر |
| سجلات مربوطة بمشروع بالاسم (D3) | تقرير بالأسماء غير المطابقة يتراجع يدويًا **قبل** الترحيل |
| المرفقات (D6) | تتنقل metadata متعلّمة «مفقود» لحد ما الملفات تتوفر |
| تشغيل migration على إنتاج | مفيش إنتاج لسه؛ القاعدة: مراجعة SQL + نسخة احتياطية مختبَرة + تجربة على نسخة + خطة rollback (كل migration فيه `down` ومتجرّب) |

## 6. أسئلة محتاجة قرار (تأثر على صحة البيانات)

1. **المحاسبة بالقيد المزدوج**: هل مطلوب دليل حسابات وقيود يومية فعلًا (موديول جديد كبير)، ولا «الحسابات» = اللي موجود (دفتر موردين + مصاريف + إيرادات)؟
2. **التقريب**: كام خانة عشرية للأموال (الإعداد الحالي `moneyDecimals`) وطريقة التقريب في الضرائب والخصم؟
3. **اعتماد المستندات المالية**: مين يعتمد فاتورة/دفعة، وبعد الاعتماد التصحيح يبقى بإشعار/مستند عكسي؟ (ده بيغيّر سلوك موجود: دلوقتي التعديل والحذف مسموحين.)
4. **أرقام المستندات**: هل لازم تسلسل من غير فجوات لكل نوع/سنة؟
