# 1. الهدف الرئيسي للمشروع

تحويل البرنامج الحالي إلى نظام ERP Web App مؤسسي متكامل، يعمل مركزيًا على سيرفر داخل الشركة، ويسمح لعدة موظفين بالعمل في نفس الوقت من أجهزة الكمبيوتر والهواتف.

يجب أن يحافظ النظام على جميع وظائف البرنامج الأصلي، مع تطوير البنية التقنية وتحسين الأداء والأمان وقابلية التوسع.

### الأهداف الأساسية

1. الحفاظ على جميع الوظائف الحالية وعدم فقدان أي ميزة.
2. توحيد جميع الموديولات داخل نظام مركزي.
3. ربط جميع البيانات بقاعدة بيانات PostgreSQL.
4. دعم تعدد المستخدمين والعمل المتزامن.
5. تطبيق نظام صلاحيات تفصيلي.
6. إنشاء دورة عمل واعتمادات رسمية.
7. ضمان سلامة البيانات المالية والمخزنية.
8. توفير نظام نسخ احتياطي واستعادة متكامل.
9. تسجيل جميع العمليات والتعديلات.
10. توفير إمكانية تحديث النظام دون فقدان البيانات.

# 2. المعمارية التقنية للنظام (System Architecture)

## 2.1 Frontend

**Technology: Angular 18+**

- استخدام Angular Standalone Components.
- تقسيم النظام إلى Feature Modules حسب الموديولات الرئيسية.
- استخدام Angular Material مع تصميم UI مخصص.
- استخدام Responsive Design لدعم الكمبيوتر والتابلت والموبايل.
- دعم PWA لتثبيت النظام على الأجهزة.
- استخدام Angular Signals وRxJS لإدارة الحالة والتفاعلات.
- استخدام Lazy Loading لتحميل الموديولات عند الحاجة.
- إنشاء مكونات مشتركة قابلة لإعادة الاستخدام.

## 2.2 Backend

**Technology: NestJS + Node.js**

اعتماد Modular Monolith Architecture.

- تقسيم Backend إلى Modules مستقلة منطقيًا.
- استخدام RESTful API.
- تطبيق DTO Validation.
- استخدام Authentication وAuthorization.
- تطبيق Transactions للعمليات المالية والمخزنية.
- استخدام Guards وInterceptors وPipes.
- توثيق API باستخدام Swagger / OpenAPI.
- فصل Business Logic عن Controllers.

## 2.3 Database

**Technology: PostgreSQL**

قاعدة بيانات مركزية لجميع الموديولات.

- استخدام Schema منظم.
- استخدام Primary Keys وForeign Keys.
- استخدام Indexes لتحسين الأداء.
- استخدام Constraints لمنع البيانات غير الصحيحة.
- استخدام NUMERIC / DECIMAL للمبالغ المالية.
- استخدام Database Transactions.
- استخدام Migrations لإدارة تغييرات قاعدة البيانات.
- استخدام Soft Delete للبيانات التي تحتاج الاحتفاظ بتاريخها، دون استخدامه بدلًا من سجل العمليات.

## 2.4 Server & Deployment

- Linux Server داخل الشركة.
- PostgreSQL.
- Docker + Docker Compose.
- Nginx Reverse Proxy.
- HTTPS باستخدام شهادة موثوقة أو شهادة داخلية مُدارة.
- Firewall.
- Static IP.
- فصل بيئات Development وTesting وProduction.
- إعداد Logs وMonitoring.
- إعداد آلية تحديث وإرجاع الإصدار السابق Rollback.

- dto
- guards
- decorators
- interceptors
- common

- tests

# 6. نظام المستخدمين والصلاحيات (Authentication & RBAC)

يجب أن يدعم النظام صلاحيات تفصيلية على أربعة مستويات:

### المستوى الأول: Module Permissions
تحديد الموديولات التي يمكن للمستخدم الدخول إليها.

### المستوى الثاني: Page Permissions
تحديد الصفحات التي يستطيع المستخدم فتحها.

### المستوى الثالث: Action Permissions
تحديد الإجراءات المسموح بها:

- View
- Create
- Edit
- Delete
- Approve
- Reject
- Print
- Export
- Pay
- Cancel

### المستوى الرابع: Data Scope Permissions
تحديد نطاق البيانات التي يمكن للمستخدم الاطلاع عليها.

مثال:

- جميع المشروعات.
- مشروعات محددة.
- مشروعات الإدارة التابعة له.
- المعاملات التي أنشأها فقط.

### متطلبات الأمان

- Password Hashing باستخدام خوارزمية آمنة.
- HttpOnly Secure Cookies عند استخدام JWT.
- Refresh Token Rotation.
- حماية CSRF حسب آلية المصادقة.
- Rate Limiting.
- حماية Endpoints على Backend.
- تسجيل محاولات الدخول الفاشلة.
- إبطال الجلسات عند الحاجة.
- عدم الاعتماد على Angular Guards وحدها لحماية البيانات.

# 10. التكامل بين الموديولات (Module Integration)

يجب ألا تعمل الموديولات كبرامج منفصلة.

أمثلة على التكامل المطلوب:

### المشاريع والحسابات
المشروع ← العقد ← المستخلصات ← التحصيلات ← الإيرادات والتكاليف ← ربحية المشروع.

### المشتريات والمخازن
طلب شراء ← اعتماد ← أمر شراء ← استلام أصناف ← إضافة للمخزون ← فاتورة المورد ← مستحقات المورد.

### الموردون والحسابات
فاتورة مورد ← مراجعة ← اعتماد ← قيد محاسبي ← دفعة ← كشف حساب المورد.

### العمالة والموارد البشرية
تسجيل العمالة ← التسكين بالمشروع ← الحضور أو المستحقات ← مراجعة ← اعتماد ← الصرف.

### المعدات والمشروعات
تسجيل المعدات ← تخصيص للمشروع ← تشغيل وصيانة ← مصروفات المعدات ← تكلفة المشروع.

### المستندات والمشروعات
إنشاء مشروع ← ملف المشروع ← العقود ← الاشتراطات ← أوامر الإسناد ← المستندات الإدارية ← الأرشفة.

# 11. قواعد سلامة العمليات المالية والمخزنية

1. منع اعتماد قيد محاسبي غير متوازن.
2. منع تكرار تنفيذ الدفعة بسبب إعادة إرسال الطلب.
3. استخدام Idempotency عند العمليات الحساسة.
4. منع صرف مستحقات تتجاوز الرصيد المسموح دون إجراء معتمد.
5. منع صرف مخزون غير متاح.
6. تسجيل كل حركة مخزنية.
7. تسجيل كل عملية مالية.
8. استخدام Transactions عند تنفيذ عمليات مترابطة.
9. منع تعديل المستندات المالية المعتمدة مباشرة.
10. إنشاء مستندات تسوية أو عكس عند الحاجة.
11. توحيد حساب الضرائب والخصومات والاستقطاعات.
12. الاحتفاظ بتاريخ التغييرات والاعتمادات.

# 12. التحديث والصيانة (Update & Maintenance)

يجب أن يدعم النظام التحديث دون حذف البيانات أو إعادة تثبيت البرنامج بالكامل.

- Versioning واضح.
- Database Migrations.
- Backup قبل التحديث.
- اختبار التحديث في بيئة Testing.
- إمكانية Rollback.
- الاحتفاظ بإعدادات النظام.
- عدم استبدال بيانات المستخدمين أثناء التحديث.
- تسجيل إصدارات البرنامج والتغييرات.

# 13. معايير قبول المشروع النهائي (Acceptance Criteria)

لا يعتبر النظام مكتملًا إلا عند تحقق الشروط التالية:

1. جميع وظائف البرنامج الأصلي موجودة أو تم توثيق التغييرات المعتمدة.
2. جميع الموديولات تعمل على قاعدة بيانات مركزية.
3. لا توجد بيانات تجريبية بدل بيانات التشغيل.
4. دعم تعدد المستخدمين دون تعارض.
5. تطبيق الصلاحيات على Backend.
6. سلامة الحسابات المالية والمخزنية.
7. وجود Audit Log.
8. وجود Workflow واعتمادات.
9. وجود نظام مستندات وأرشيف.
10. وجود Backup & Restore تم اختباره.
11. وجود اختبارات Functional وIntegration.
12. عمل النظام بعد إعادة تشغيل السيرفر.
13. دعم PWA.
14. وجود مراقبة للأداء والأخطاء.
15. إمكانية التحديث دون فقد البيانات.
16. توثيق البنية وقاعدة البيانات والـ APIs.
17. اختبار استعادة النظام في حالة تعطل السيرفر.

# 14. قواعد إلزامية أثناء التطوير

- ممنوع حذف أي وظيفة من البرنامج الأصلي دون موافقة.
- ممنوع استبدال الوظائف الحقيقية بواجهات شكلية.
- ممنوع استخدام بيانات وهمية لإظهار أن الموديول يعمل.
- ممنوع وضع Business Logic داخل Frontend.
- ممنوع تجاوز الصلاحيات من خلال API.
- ممنوع تعديل قاعدة البيانات يدويًا دون Migration موثق.
- ممنوع اعتبار الموديول مكتملًا بمجرد تشغيل الصفحة.
- يجب اختبار كل عملية من البداية حتى النهاية.
- يجب توثيق كل قرار معماري مهم.
- يجب مراجعة الكود قبل دمج أي تعديل كبير.
- يجب الحفاظ على البيانات الموجودة عند تحديث النظام.
- يجب عدم الانتقال إلى المرحلة التالية قبل اجتياز معايير قبول المرحلة الحالية.
