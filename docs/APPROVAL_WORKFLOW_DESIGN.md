# تصميم محرك الاعتمادات (Approval Workflow Design)

- **التاريخ:** 2026-11-16 · **آخر تحديث:** 2026-11-17 (ربط بقرارات NO_GAPS و4 خانات HALF_UP) · **الحالة:** تصميم مقترح — لم يُنفَّذ منه شيء. لا تعديل على الكود أو قاعدة البيانات.
- **القرار الحاكم:** ADR-003 (اعتمادات متعددة المستويات، قابلة للتهيئة) وADR-012 (الفصل بين `Approved` و`Posted`).

> ## ⚠️ قيم غير محددة عمدًا
> هذا التصميم **لا يحتوي** أي حد مالي، ولا مسمى وظيفي، ولا عدد مستويات. كل ما يظهر بين `‹…›` هو **إعداد فارغ يحتاج قرار إدارة الشركة** (مصفوفة الاعتماد — `OPEN_BUSINESS_DECISIONS.md` بند B-01). الأمثلة الواردة للتوضيح تستخدم رموزًا مجرّدة (`‹حد-1›`، `‹دور-أ›`) وليست اقتراحات.

## 2. المبادئ

1. **الاعتماد في الخادم فقط.** إخفاء الأزرار في الواجهة ليس حماية.
2. **التهيئة بيانات لا كود:** أنواع المستندات، الحدود، المستويات، المعتمدون — كلها جداول إعدادات.
3. **انتقالات الحالة عبر أوامر محددة** (`submit`, `approve`, …). لا يوجد مسار يكتب حقل الحالة مباشرة.
4. **مقدّم الطلب لا يعتمد مستنده** افتراضيًا.
5. **`Approved` ≠ `Posted`.** الترحيل خطوة مستقلة بصلاحية مستقلة.
6. **كل قرار مسجَّل:** مَن، متى، أي مستوى، القرار، الملاحظات.
7. **تغيير جوهري = إعادة تقييم.** تغيير القيمة أو البيانات الجوهرية يعيد حساب المسار.
8. **نسخة التعريف ثابتة لكل طلب:** تعديل الإعدادات لا يغيّر مسار طلبات جارية.
9. **الترقيم NO_GAPS (Confirmed — ADR-013):** المستند المرقّم الذي يُرفض أو يُلغى **يحتفظ برقمه** وسجل قراره؛ لا يُحذف (ADR-024). متى يُصدر الرقم (عند الحفظ أم عند `submit`) جزء من B-29.
10. **مقارنة حدود القيمة بـ `NUMERIC` بعد تقريب القيمة لـ 4 خانات HALF_UP** (Confirmed — ADR-011)، حتى لا تختلف نتيجة اختيار المسار بسبب كسور.

## 3. الحالات والانتقالات

```
                      submit                 (أول قرار)                (آخر مستوى)            post
   ┌───────┐  ─────────────▶ ┌───────────┐ ───────────▶ ┌──────────────┐ ──────────▶ ┌──────────┐ ─────▶ ┌────────┐
   │ Draft │                 │ Submitted │              │ Under Review │             │ Approved │        │ Posted │
   └───┬───┘ ◀───────────── └─────┬─────┘              └──┬───────┬───┘             └────┬─────┘        └───┬────┘
       │        withdraw          │                       │       │                      │                  │ reverse
       │                          │ reject                │reject │ return               │ cancel           ▼
       │                          ▼                       ▼       ▼                      ▼             ┌──────────┐
       │                     ┌──────────┐            ┌──────────┐ ┌──────────┐      ┌───────────┐      │ Reversed │
       │                     │ Rejected │            │ Rejected │ │ Returned │      │ Cancelled │      └──────────┘
       │                     └──────────┘            └──────────┘ └────┬─────┘      └───────────┘
       │ cancel                                                        │ resubmit (بعد التعديل)
       ▼                                                               ▼
  ┌───────────┐                                                   Submitted (دورة جديدة)
  │ Cancelled │
  └───────────┘
```

| الحالة | المعنى | التعديل على المستند |
|---|---|---|
| `Draft` | مسودة لدى مُنشئها | مسموح لصاحب صلاحية التعديل |
| `Submitted` | أُرسل وحُسب مساره وينتظر أول قرار | **مقفل** |
| `Under Review` | صدر قرار واحد على الأقل وبقيت مستويات | **مقفل** |
| `Approved` | اكتملت كل المستويات | **مقفل** — لا أثر مالي بعد |
| `Posted` | رُحِّل وأُنشئ أثره (قيد محاسبي / حركة) | **ممنوع نهائيًا** — التصحيح بعكس |
| `Rejected` | رُفض نهائيًا | مقفل (يمكن نسخه لمسودة جديدة — قرار مفتوح) |
| `Returned` | أُعيد للتصحيح | مسموح لمُنشئه، ثم `resubmit` |
| `Cancelled` | أُلغي قبل الترحيل | مقفل |
| `Reversed` | عُكس بعد الترحيل بمستند عكسي مرتبط | مقفل |

### جدول الانتقالات المسموحة (كل ما عداه مرفوض)
| من | الأمر | إلى | مَن | شروط |
|---|---|---|---|---|
| Draft | `submit` | Submitted | مُنشئ المستند / صاحب صلاحية الإرسال | المستند صالح؛ يوجد تعريف مسار مطابق |
| Draft | `cancel` | Cancelled | مُنشئه / صاحب صلاحية الإلغاء | سبب إلزامي |
| Submitted, Under Review | `approve` | Under Review أو Approved | معتمِد مخوَّل في المستوى الحالي | ليس مقدّم الطلب (افتراضيًا)؛ لم يقرر سابقًا في نفس المستوى |
| Submitted, Under Review | `reject` | Rejected | معتمِد مخوَّل في المستوى الحالي | سبب إلزامي |
| Submitted, Under Review | `return` | Returned | معتمِد مخوَّل في المستوى الحالي | سبب إلزامي |
| Submitted | `withdraw` | Draft | مقدّم الطلب | لم يصدر أي قرار بعد |
| Returned | `resubmit` | Submitted | مُنشئه | دورة جديدة؛ إعادة تقييم المسار |
| Approved | `post` | Posted | صاحب صلاحية الترحيل | الفترة المالية مفتوحة؛ القيد متوازن |
| Approved | `cancel` | Cancelled | صاحب صلاحية الإلغاء | سبب إلزامي |
| Posted | `reverse` | Reversed | صاحب صلاحية العكس | يُنشأ مستند عكسي؛ **هل العكس نفسه يحتاج اعتمادًا؟ — قرار مفتوح** |

## 5. قواعد السلوك

### 5.1 اختيار المسار عند `submit`
1. قراءة نوع المستند وقيمته من **الخادم** (لا من الطلب).
2. اختيار تعريف المسار الفعّال الذي يطابق النوع ونطاق القيمة (والشروط الإضافية إن وُجدت).
3. **لا تعريف مطابق ← رفض الإرسال برسالة واضحة.** لا يوجد «اعتماد تلقائي» افتراضي. (هل تُعفى مستندات من الاعتماد؟ — قرار مفتوح، ويُنفَّذ كتعريف صريح «بلا مستويات» لا كغياب تعريف.)
4. نسخ المستويات والمعتمدين إلى الطلب (لقطة) وتسجيل `material_hash`.

### 5.2 المتتابع والمتوازي
- المستويات تُنفَّذ بترتيب `sequence` تصاعديًا.
- داخل المستوى: `ALL` (كل المعتمدين)، `ANY` (أي واحد)، `N_OF_M` (عدد محدد) — العدد **‹إعداد›**.
- لا يُفتح مستوى قبل اكتمال السابق.
- أي `REJECT` أو `RETURN` في أي مستوى يُنهي الدورة فورًا.

### 5.3 الفصل بين المهام
- مقدّم الطلب ومُنشئ المستند لا يعتمدانه — حتى لو كانا ضمن المعتمدين. الاستثناء **‹إعداد صريح يحتاج قرار الإدارة›** ويُسجَّل استخدامه.
- المستخدم لا يقرر أكثر من مرة في نفس المستوى.
- هل يجوز لنفس المستخدم الاعتماد في مستويين مختلفين من نفس الطلب؟ — **قرار مفتوح** (الافتراضي المقترح: لا).
- مَن يعتمد لا يُرحِّل نفس المستند؟ — **قرار مفتوح**.

### 5.4 التفويض المؤقت
- المفوَّض إليه يعتمد **بالنيابة**؛ القرار يسجّل الاثنين (`decided_by` و`on_behalf_of`).
- التفويض محدد بمدة ونطاق؛ ينتهي تلقائيًا.
- لا يجوز التفويض إلى مقدّم الطلب نفسه؛ لا تفويض متسلسل (المفوَّض لا يفوِّض) — افتراضي مقترح، **قابل للقرار**.
- مَن يحق له إنشاء التفويض (المفوِّض نفسه / الإدارة)؟ — **قرار مفتوح**.

### 5.5 القفل أثناء الاعتماد
- في `Submitted` / `Under Review` / `Approved`: الخادم يرفض أي تعديل على **الحقول الجوهرية** للمستند.
- الحقول غير الجوهرية (ملاحظات، مرفقات إضافية): مسموحة أم لا؟ — **‹إعداد لكل نوع مستند›**.
- للتعديل: `return` من معتمِد أو `withdraw` من المقدّم (قبل أي قرار).

### 5.6 إعادة التقييم
- عند `resubmit`: يُعاد حساب المسار من الصفر بقيمة المستند الحالية؛ القرارات السابقة تبقى في السجل لكنها **لا تُحتسب**.
- حماية إضافية: عند كل `approve` وعند `post` يُقارَن `material_hash` الحالي بالمسجَّل؛ الاختلاف ← إبطال الطلب وإعادته إلى `Draft` مع تسجيل السبب (يكشف أي تعديل تجاوز القفل).

### 5.7 الترحيل (`post`)
- صلاحية مستقلة (`Post`).
- داخل **معاملة واحدة**: التحقق من الحالة `Approved` ← التحقق من الفترة المالية ← إنشاء القيد المتوازن (موديول Accounting) ← تغيير الحالة إلى `Posted`.
- فشل أي خطوة = تراجع كامل.
- **Idempotency:** مفتاح فريد لكل عملية ترحيل؛ إعادة الإرسال لا تنشئ قيدًا ثانيًا.

### 5.8 الإشعارات
- عند فتح مستوى: إشعار لمعتمديه. عند القرار النهائي/الإرجاع: إشعار للمقدّم.
- القنوات (داخل النظام فقط / بريد داخلي) — **قرار مفتوح**. التصعيد عند التأخر والمدد — **قرار مفتوح**.

## 6. منع التلاعب عبر API

| التهديد | الحماية |
|---|---|
| كتابة حقل الحالة مباشرة | الحالة ليست ضمن أي DTO للكتابة؛ تتغير فقط عبر أوامر المحرك. في فترة الواجهة الحالية: طبقة التوافق (`/api/sync`) **ترفض** أي تغيير على حقول الحالة والحقول الجوهرية لمستند غير `Draft`/`Returned` |
| اعتماد بلا تخويل | التحقق في الخادم من أن المستخدم (أو مفوِّضه) ضمن معتمدي **المستوى الحالي** في **لقطة** الطلب |
| اعتماد المقدّم لمستنده | مقارنة هوية المقرِّر بالمقدّم والمُنشئ من سجلات الخادم |
| تغيير القيمة لتفادي مستوى أعلى | القيمة تُقرأ من القاعدة؛ القفل + `material_hash` + إعادة التقييم |
| تكرار القرار / السباق | قيد فريد على القرار + قفل صف الطلب + `row_version` (تعارض ← 409) |
| ترحيل مكرر | مفتاح Idempotency + قيد فريد (مستند ← قيد واحد) |
| تجاوز عبر تعديل الإعدادات أثناء الطلب | اللقطة: الطلبات الجارية تتبع النسخة التي أُرسلت عليها |
| تعديل سجل القرارات | جداول إلحاق فقط محمية على مستوى القاعدة |
| وصول لمستند خارج النطاق | صلاحيات نطاق البيانات (المشروع/الإدارة) تُطبَّق قبل أي أمر |

## 8. التكامل مع الموجود

| الجانب | الأثر |
|---|---|
| الواجهة الحالية | لا تعرف الحالات. عند تفعيل نوع مستند: يُضاف له في الواجهة الحالية عرض الحالة وأزرار الأوامر (تعديل محدود يُخطَّط له)، أو يُفعَّل الاعتماد لهذا النوع فقط بعد نقل شاشته إلى Angular — **قرار تنفيذي مفتوح لكل نوع** |
| المستندات القائمة | حالتها الابتدائية عند التفعيل (مثلًا اعتبارها مرحّلة تاريخيًا) — **قرار مفتوح** يؤثر على الأرصدة الافتتاحية |
| الصلاحيات | إضافة أفعال Approve / Reject / Post / Cancel / Reverse (ADR-016) |
| سجل التدقيق | كل أمر يُسجَّل في `approval_state_log` وفي Audit Log |
| المحاسبة | `post` يستدعي خدمة الترحيل (`ACCOUNTING_ROADMAP.md`) |

**ترتيب التنفيذ المقترح:** المحرك وإعداداته واختباراته ← تفعيله على نوع واحد منخفض المخاطر ← باقي الأنواع بقرار لكل نوع.

## 9. حالات الاختبار

> الرموز `‹حد-1›` < `‹حد-2›`، `‹دور-أ›`… قيم اختبار تُعرَّف داخل الاختبار فقط.

### 9.1 النجاح
| # | الحالة | المتوقع |
|---|---|---|
| A-01 | إرسال مستند قيمته ضمن نطاق مسار بمستوى واحد ثم اعتماده | Submitted ← Approved؛ قرار واحد مسجَّل |
| A-02 | مسار بمستويين متتابعين | بعد القرار الأول Under Review؛ بعد الثاني Approved |
| A-03 | مستوى `ALL` بمعتمدَين | لا ينتقل إلا بعد قرار الاثنين |
| A-04 | مستوى `ANY` | ينتقل بأول قرار؛ قرار الثاني يُرفض لأن المستوى أُغلق |
| A-05 | مستوى `N_OF_M` | ينتقل عند بلوغ العدد المطلوب بالضبط |
| A-06 | قيمة أعلى من `‹حد-1›` | يُختار المسار ذو المستويات الأكثر |
| A-07 | إرجاع ← تعديل ← إعادة إرسال | دورة جديدة؛ قرارات الدورة السابقة محفوظة وغير محتسبة |

## 10. ما يحتاج قرار الإدارة قبل التنفيذ

| # | القرار | يمنع |
|---|---|---|
| 1 | أنواع المستندات الخاضعة للاعتماد | تهيئة المحرك |
| 2 | حدود القيمة لكل نوع | تهيئة المحرك |
| 3 | عدد المستويات والمعتمدون في كل مستوى (أدوار/مستخدمون) ونمط كل مستوى | تهيئة المحرك |
| 4 | استثناءات الفصل بين المهام | التفعيل |
| 5 | قواعد التفويض | ميزة التفويض |
| 6 | الحقول الجوهرية لكل نوع مستند | القفل وإعادة التقييم |
| 7 | مَن يُرحِّل؟ وهل المعتمِد يُرحِّل؟ | التفعيل مع المحاسبة |
| 8 | هل العكس والإلغاء يحتاجان اعتمادًا؟ | مسار العكس |
| 9 | معاملة المستندات القائمة عند التفعيل | الترحيل والأرصدة الافتتاحية |
| 10 | مدد الاعتماد والتصعيد وقنوات الإشعار | الإشعارات |

**يمكن بناء المحرك واختباره بقيم اختبار قبل هذه القرارات؛ لا يمكن تفعيله على بيانات حقيقية قبلها.**
