## 3. القرارات المعتمدة (لا تُغيَّر)

Internal فقط · Angular + Angular Material · NestJS · PostgreSQL · Modular Monolith · Nginx · سيرفر داخل الشركة · المرفقات داخل PostgreSQL · قيد مزدوج كامل بتفعيل تدريجي · اعتمادات متعددة المستويات قابلة للتهيئة · **4 خانات عشرية · HALF_UP · NO_GAPS**.

**القواعد المالية والترقيم (الخطة §2):**
1. `NUMERIC` للقيم المالية — **لا `float`/`double precision` أبدًا** (VERIFIED: `float8` في PostgreSQL يقرّب 2.5 إلى 2 وفيه أخطاء تمثيل).
2. الحساب المالي الدقيق في Backend، لا في الواجهة.
3. 4 خانات + HALF_UP (التفسير: الحالة النصفية بعيدًا عن الصفر، وهو سلوك `round()` و`numeric(p,4)` في PostgreSQL — VERIFIED؛ تأكيد التفسير: B-70).
4. لا JavaScript `Number` كمصدر للحساب المالي الدقيق.
5. رقم المستند يُولَّد داخل معاملة قاعدة البيانات.
6. لا يُستهلك رقم عند فشل المعاملة.
7. المستند الملغى يحتفظ برقمه وسجل إلغائه.
8. لا يُحذف أثر المستند الملغى.

## 4. دورة كل مرحلة (الخطة §12)

1. **Before Report** في `docs/reports/PHASE_XX_BEFORE_REPORT.md`: الوضع، الملفات المتأثرة، الاختبارات، المخاطر، الاعتماديات، القرارات، خطة الرجوع.
2. **Approval**: موافقة المستخدم على النطاق.
3. **Implementation**: المرحلة المحددة فقط — وداخل مراحل النقل، موديول واحد فقط.
4. **Testing**: تشغيل الاختبارات وتوثيق النتائج الفعلية (لا ادعاء نجاح دون تشغيل).
5. **After Report** في `docs/reports/PHASE_XX_AFTER_REPORT.md`: ملخص، الملفات، التغييرات، الاختبارات، معايير القبول وحالة كل منها، القرارات المفتوحة، المخاطر، خطة الرجوع، توصية الجاهزية.
6. **Review & Approval**: **التوقف** وانتظار موافقة صريحة. **لا انتقال تلقائي.**

تحديث `IMPLEMENTATION_BACKLOG.md` و`ERP_RISK_REGISTER.md` في نهاية كل مرحلة.

## 5. الممنوعات

- حذف أو تعطيل أي وظيفة أو صفحة أو حقل أو معادلة دون موافقة صريحة.
- تغيير معادلة أو قاعدة عمل بالتخمين.
- اختراع: حدود اعتماد، نسب ضرائب أو خصومات، دليل حسابات، أدوار أو مسميات وظيفية، عدد مستويات، قيم RPO/RTO.
- Migration أو أوامر مدمرة (`DROP`, `TRUNCATE`, `RESET`, حذف جماعي) على بيانات حقيقية دون موافقة صريحة **ونسخة احتياطية مُستعادة بنجاح**.
- تفعيل الاعتمادات أو المحاسبة على بيانات حقيقية قبل اعتماد السياسات.
- الدمج بين `Approved` و`Posted`.
- حماية بالواجهة فقط.
- وضع أسرار في الكود أو git؛ طباعة أسرار أو بيانات شخصية في التقارير (البيانات الحقيقية: أعداد فقط).
- رفع ملف `data.json` الحقيقي أو أي بيانات شخصية إلى git (موجود خارج المستودع فقط).
- توسيع نطاق المرحلة دون موافقة.

## 7. معايير قبول المراحل (Phase Acceptance Criteria)

> كل معيار يُثبت بدليل (اختبار أو مراجعة موثّقة). «موافقة المستخدم» معيار أخير لكل مرحلة.

### المرحلة 1 — توحيد التقارير والتخطيط المعماري
- P1-1 الخطة الرئيسية محفوظة في `docs/` بلا تعديل.
- P1-2 القرارات المعتمدة (بما فيها 4 خانات/HALF_UP/NO_GAPS) مثبّتة في ADR وOPEN_BUSINESS_DECISIONS؛ B-25 وB-30 محسومان؛ B-20, B-26, B-27, B-29 مفتوحة.
- P1-3 `MODULE_DEPENDENCY_MAP.md` مبني على تحليل فعلي للكود والبيانات ويجيب الأسئلة الخمسة لكل موديول.
- P1-4 `MODULE_MIGRATION_PLAN.md`, `SECURITY_AND_BACKUP_PLAN.md`, `ERP_RISK_REGISTER.md`, هذه الوثيقة موجودة.
- P1-5 `IMPLEMENTATION_BACKLOG.md` مربوط بالمراحل الـ 12.
- P1-6 التعارضات بين الوثائق موثّقة ومحلولة لصالح المرجع الأعلى.
- P1-7 لا تغيير في كود التطبيق أو قاعدة البيانات (`git diff` على `renderer/ src/ server/ web/ docker/` فارغ).

### المرحلة 2 — تأمين النظام
- P2-1 اختبار حقن XSS آلي على كل الحقول النصية وكل الصفحات: صفر تنفيذ.
- P2-2 ترويسات الأمان مفعّلة؛ CSP بلا انتهاكات عند تشغيل كل الصفحات (Report-Only ثم إنفاذ).
- P2-3 Nginx + HTTPS داخلي يعمل للواجهة والـ API والـ WebSocket؛ لا منافذ للخادم أو القاعدة خارج Compose.
- P2-4 مصفوفة الصلاحيات تمر؛ لا مسار بلا حارس؛ فحص `Origin` على مسارات الكوكي.
- P2-5 رفع الملفات: رفض الامتداد المزيف وتجاوز الحجم؛ تنزيل خارج النطاق ← 403.
- P2-6 سجل التدقيق يحفظ القيمة السابقة؛ تعديله على مستوى القاعدة يفشل.
- P2-7 نسخ احتياطي + **استعادة ناجحة موثّقة على بيئة منفصلة** مع مطابقة الأعداد والبصمات.
- P2-8 الـ 58 ملف اختبار واجهة ما زالت تمر (في الوضعين).

### المرحلة 3 — توثيق النظام القديم وقواعد العمل
- P3-1 لكل موديول: وثيقة قواعد عمل ومعادلات بالملف والسطر وأمثلة رقمية.
- P3-2 كل معادلة مالية ومخزنية لها اختبار مرجعي مباشر يمر على النظام الحالي.
- P3-3 الصفحات الـ 54: كل صفحة لها اختبار قبول لعملياتها (إضافة/تعديل/حذف/طباعة/تصدير حسب ما فيها).
- P3-4 حالات المستندات ودورات العمل الحالية موثّقة (بما فيها ما لا يوجد).
- P3-5 الصلاحيات والمدخلات والمخرجات موثّقة لكل صفحة.
- P3-6 لا تغيير في سلوك الواجهة الحالية.

### المرحلة 4 — تجهيز البنية التقنية النهائية
- P4-1 مشروع Angular + Material بواجهة عربية RTL وPWA قابلة للتثبيت، يدخل بنفس الجلسة ويقرأ الصلاحيات من الخادم.
- P4-2 هيكل NestJS بالطبقات الأربع (Presentation/Services/Data/Utilities) موثّق ومطبّق في موديول تجريبي.
- P4-3 أداة حساب عشري في الخادم بـ 4 خانات HALF_UP مع اختبارات حدود (سالب، .5 الدقيقة، كسور التمثيل).
- P4-4 Transactions وValidation وLogging موحّدة؛ بيئات Development/Testing منفصلة.
- P4-5 لا كسر للواجهة الحالية.

### المرحلة 5 — بناء الأساس المشترك
- P5-1 الصلاحيات بالمستويات الأربعة (موديول/صفحة/فعل/نطاق) مختبرة بمصفوفة.
- P5-2 المشروعات والبيانات الأساسية في جداول علائقية؛ كل السجلات مربوطة بالمعرّف (B-34).
- P5-3 المرفقات داخل PostgreSQL: رفع/تنزيل متدفق، بصمة، إصدارات، صلاحيات، ضمن النسخ والاستعادة.
- P5-4 Audit Log كامل (قبل/بعد، سبب الإلغاء/الرفض) ومحمي.
- P5-5 محرك الاعتمادات يمر كل حالات `APPROVAL_WORKFLOW_DESIGN.md §9` **ببيانات اختبار**؛ غير مفعّل على بيانات حقيقية.
- P5-6 الترقيم NO_GAPS: لا تكرار تحت التزامن، لا استهلاك عند الفشل، الملغى يحتفظ برقمه.
- P5-7 Idempotency: إعادة إرسال عملية حساسة لا تكررها.
- P5-8 الإشعارات المخزّنة تعمل.
