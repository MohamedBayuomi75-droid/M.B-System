# ERP MASTER IMPLEMENTATION PLAN
## الخطة الرئيسية لتنفيذ نظام ERP لشركة المقاولات

**الإصدار:** 1.0  
**التاريخ:** 16 نوفمبر 2026  
**الحالة:** خطة تنفيذ موحدة للمراجعة والاعتماد  
**نطاق النظام:** Internal ERP — شركة مقاولات عامة

---

## 1. الهدف

تطوير نظام ERP متكامل لإدارة شركة المقاولات، بالاعتماد على النظام الحالي وبياناته وقواعد العمل الموجودة فيه، مع تطوير البنية التقنية تدريجيًا دون فقدان أي وظيفة أو بيانات.

يشمل النظام:

- المشروعات والعقود والمستخلصات.
- العملاء والموردين.
- المشتريات والفواتير والمرتجعات.
- المخازن وحركة الأصناف.
- الخزينة والبنوك والمدفوعات والتحصيلات.
- المحاسبة وتكاليف المشروعات.
- العمالة والموظفون والمعدات.
- السلامة والمخاطر.
- الجودة والاستلام.
- سير العمل والاعتمادات.
- التقارير ولوحات المعلومات.
- المستخدمون والصلاحيات.
- الأرشفة والمرفقات وسجل المراجعة.
- النسخ الاحتياطي والاستعادة.

**المبدأ الأساسي:** تطوير النظام الحالي تدريجيًا، موديولًا بموديول، وليس استبداله دفعة واحدة.

## 2. القرارات المعتمدة

هذه القرارات ثابتة ويجب الالتزام بها في جميع التصميمات والتنفيذات:

| البند | القرار |
|---|---|
| نطاق الوصول | Internal فقط |
| Frontend | Angular |
| UI Library | Angular Material |
| Backend | NestJS |
| Database | PostgreSQL |
| Architecture | Modular Monolith |
| Reverse Proxy | Nginx |
| Deployment | سيرفر داخل الشركة |
| Attachments | داخل PostgreSQL |
| المحاسبة | قيد مزدوج كامل مع تفعيل تدريجي |
| الاعتمادات | متعددة المستويات وقابلة للتهيئة |
| الدقة المالية | 4 خانات عشرية |
| التقريب | HALF_UP |
| ترقيم المستندات | NO_GAPS |

### قواعد مالية وترقيم إلزامية

1. استخدام PostgreSQL `NUMERIC` للقيم المالية.
2. تنفيذ الحسابات المالية الدقيقة في Backend، وليس في الواجهة.
3. الالتزام بدقة 4 خانات عشرية وبطريقة تقريب `HALF_UP`.
4. عدم استخدام JavaScript `Number` كمصدر للحسابات المالية الدقيقة.
5. توليد أرقام المستندات داخل معاملة قاعدة البيانات.
6. لا يُستهلك رقم عند فشل المعاملة.
7. المستند الذي أُصدر رقمه ثم أُلغي يحتفظ برقمه وسجل إلغائه.
8. لا يُحذف أثر المستندات الملغاة.

## 3. الوضع الحالي وفق تقارير الفحص

### النظام القديم

- تطبيق Electron.
- تخزين البيانات في `data.json`.
- واجهة Vanilla JavaScript كبيرة.
- ملف البيانات نحو 1.54MB ويحتوي على 53 مجموعة بيانات.
- توجد سجلات للفواتير والموردين والمدفوعات والعمالة والمشروعات والتكاليف وغيرها.

### النسخة الانتقالية

- NestJS وPostgreSQL 16.
- تخزين بعض سجلات الأعمال في `records` باستخدام JSONB.
- وجود migrations أولية.
- وجود أنظمة للمستخدمين والصلاحيات وسجل التغييرات.
- وجود اختبارات للمعاملات والترحيل التجريبي وبعض العمليات المتزامنة.

### البنية المستهدفة

- Angular + Angular Material.
- NestJS API.
- PostgreSQL.
- Nginx وHTTPS.
- Modular Monolith.
- Docker Compose.
- تطبيق Web داخلي قابل للتثبيت PWA.

> هذه الحالة مستخلصة من التقارير المقدمة. يجب على Claude Code التحقق من الكود والاختبارات الفعلية قبل اعتبار أي عنصر منفذًا. وجود تصميم أو تقرير لا يثبت التنفيذ.

## 4. المبادئ الحاكمة

1. لا حذف لأي وظيفة موجودة دون موافقة صريحة.
2. لا حذف أو تعديل للبيانات الأصلية دون خطة معتمدة.
3. لا استبدال شامل للنظام دفعة واحدة.
4. لا نقل لأي موديول قبل توثيق قواعد عمله ومعادلاته.
5. لا تغيير للمعادلات الحالية اعتمادًا على التخمين.
6. لا اختراع نسب ضرائب أو خصومات أو حدود اعتماد.
7. لا اختراع دليل حسابات أو أدوار وظيفية.
8. لا تشغيل محاسبي حقيقي قبل اعتماد السياسات.
9. لا تنفيذ migrations على بيانات حقيقية دون موافقة صريحة ونسخة احتياطية قابلة للاستعادة.
10. كل مرحلة لها تقرير قبل التنفيذ وتقرير بعد التنفيذ.
11. كل تغيير محدود النطاق وقابل للمراجعة والرجوع.
12. يجب الفصل بين التصميم المقترح والتنفيذ الفعلي في الوثائق.

## 5. البنية التقنية المستهدفة

### Frontend

Angular + Angular Material، مع:

- واجهة عربية RTL.
- مكونات مشتركة وقابلة لإعادة الاستخدام.
- جداول ونماذج إدخال موحدة.
- تطبيق صلاحيات الواجهة.
- عدم وضع المعادلات المالية داخل الواجهة.
- فصل Presentation عن Business Logic.

### Backend

NestJS بنمط Modular Monolith، مع فصل:

- Modules.
- Controllers.
- Services.
- Repositories / Data Access.
- DTOs.
- Guards.
- Validation.
- Transactions.
- Events / Notifications.

### Database

PostgreSQL، مع:

- جداول علائقية للموديولات بعد نقلها.
- Foreign Keys وUnique Constraints وCheck Constraints.
- Indexes مناسبة.
- `NUMERIC` للقيم المالية.
- Transactions للعمليات الحساسة.
- سجل تغييرات قابل للتتبع.
- استخدام JSONB بصورة انتقالية للتوافق فقط، مع خطة لتحويل كل موديول إلى جداول علائقية عند نقله.

### تنظيم الكود

الالتزام بأربع طبقات:

1. Presentation.
2. Services.
3. Data.
4. Utilities.

تكون قواعد العمل والمعادلات في Services، وليس داخل عناصر الواجهة.

## 6. محرك الاعتمادات

التصميم المستهدف:

- Workflow قابل للتهيئة.
- دعم مستويات متعددة.
- فصل `Approved` عن `Posted`.
- تنفيذ الاعتماد من Backend فقط.
- حفظ Snapshot لإعدادات الاعتماد وقت تقديم المستند.
- تسجيل كل قرار اعتماد.
- منع تكرار الترحيل باستخدام Idempotency.
- الاحتفاظ بسجل القرارات.
- دعم التفويض وفق سياسة تعتمدها الإدارة.

الحالات المقترحة:

`Draft`, `Submitted`, `Under Review`, `Approved`, `Posted`, `Rejected`, `Returned`, `Cancelled`, `Reversed`.

هذه حالات تصميم مقترح وليست دليلًا على وجود تنفيذ فعلي.

**لا يجوز تخمين** عدد المستويات أو الحدود المالية أو المسميات الوظيفية أو أسماء المعتمدين. لا يُفعّل المحرك على مستندات حقيقية قبل اعتماد هذه القرارات.

## 12. التقارير الإلزامية لكل مرحلة

كل مرحلة تمر بالدورة التالية:

1. **Before Report:** الوضع الحالي، الملفات المتأثرة، الاختبارات، المخاطر، الاعتماديات، القرارات المطلوبة، وخطة الرجوع.
2. **Approval:** تحديد النطاق والحصول على موافقة المستخدم.
3. **Implementation:** تنفيذ المرحلة المحددة فقط.
4. **Testing:** تشغيل الاختبارات وتوثيق النتائج.
5. **After Report:** ما نُفذ، الملفات الجديدة والمعدلة، نتائج الاختبارات، المشاكل، المخاطر المتبقية، ومقارنة النتائج بخط الأساس.
6. **Review & Approval:** مراجعة المستخدم واعتماد الانتقال للمرحلة التالية.

يجب أن يحتوي تقرير ما بعد المرحلة على:

- ملخص تنفيذي.
- الملفات التي أُنشئت أو عُدلت.
- التغييرات الفعلية.
- الاختبارات ونتائجها.
- معايير القبول وحالة كل منها.
- القرارات المفتوحة.
- المخاطر المتبقية.
- خطة الرجوع.
- توصية واضحة بشأن جاهزية المرحلة التالية.

**لا ينتقل Claude Code تلقائيًا إلى المرحلة التالية.**

## 14. معايير نجاح المشروع

يُعتبر النظام جاهزًا عندما:

- يحافظ على وظائف النظام الأصلي وبياناته.
- تكون العمليات المالية دقيقة وقابلة للمراجعة.
- تكون الاعتمادات واضحة وقابلة للتتبع.
- تكون الصلاحيات مطبقة في Backend.
- تكون العلاقات والقيود في قاعدة البيانات صحيحة.
- يمكن استعادة النظام من نسخة احتياطية تم اختبارها.
- تكون الموديولات موثقة ومختبرة.
- تكون التغييرات قابلة للمراجعة والتتبع.
- لا توجد قرارات إدارية مطبقة بناءً على التخمين.
- يتم اعتماد المطابقة والتحويل قبل إيقاف النظام القديم.

## 15. تعليمات التنفيذ النهائية إلى Claude Code

1. اعتبر هذه الوثيقة المرجع الرئيسي للخطة، مع الالتزام بالقرارات المعتمدة.
2. افحص المشروع الفعلي ولا تعتمد على التقارير السابقة وحدها عند التحقق من التنفيذ.
3. ميّز بين Confirmed Decision وRecommendation وOpen Business Decision.
4. ميّز بين Implemented وPartially Implemented وNot Implemented وNeeds Verification.
5. لا تحذف وظائف أو بيانات ولا تغيّر قواعد العمل دون موافقة صريحة.
6. لا تنفذ migrations على بيانات حقيقية دون موافقة صريحة ونسخة قابلة للاستعادة.
7. لا تخترع حدود اعتماد أو نسب ضرائب أو دليل حسابات أو أدوارًا وظيفية.
8. التزم بـ4 خانات عشرية وHALF_UP وNO_GAPS.
9. افصل دائمًا بين Approved وPosted.
10. نفّذ مرحلة واحدة فقط في كل مرة.
11. داخل مراحل نقل الموديولات، نفّذ موديولًا واحدًا في كل مرة.
12. أعد تقريرًا قبل وبعد كل مرحلة.
13. توقف بعد كل مرحلة وانتظر موافقة المستخدم الصريحة.

**القاعدة النهائية:** سلامة البيانات واستمرارية وظائف النظام أهم من سرعة التنفيذ. أي خطوة قد تسبب فقد بيانات أو تغيير قواعد العمل أو توسيع نطاق المرحلة يجب أن تتوقف عندها وتطلب موافقة صريحة.
