# موديول المخازن — قواعد المخزون والصرف (6.2)

> **الحالة:**
> - **6.2-أ (B-50):** منفّذ ومختبر.
> - **B-51 (التسويات):** منفّذ ومختبر.
> - **6.2-ب (الجداول + الـ Adapter + الـ API + Angular + أمر النقل):** منفّذ ومختبر ببيانات اختبار.
> - **التنفيذ على الخادم الفعلي:** أمر تشغيل بعد نسخة واختبار استعادة (§5).

## 1. قواعد الرصيد
- **الرصيد (صنف، مخزن)** = مجموع الحركات الحية:
  - **الإضافة:** استلام `in` وتسوية زيادة `adjust_in` بتزوّد الرصيد في المخزن.
  - **الخصم:** صرف `out` وتسوية نقص `adjust_out` بتقلّل الرصيد في المخزن.
  - **التحويل `transfer`:** بيقلّل من المخزن المصدر ويزوّد المخزن الوجهة. إجمالي الصنف مابيتغيّرش.
  - **الدالة:** `wh_balance(item, location)` في قاعدة البيانات، بنفس منطق `renderer/modules/warehouses/helpers.js:27`.
- **المتاح** = الرصيد − المحجوز النشط (`stock_reservations`) — B-50 §3.
- **الدقة:** الكميات بـ numeric من غير تقريب في الفحص (B-26 = 5 خانات). الواجهة الحالية بتدخل بخانتين.

## 2. قواعد الصرف (B-50 — معتمد ونهائي)
| القاعدة | التطبيق |
|---|---|
| **مفيش رصيد متاح سالب في أي حالة** | trigger `wh_movement_guard` على كل كتابة لحركة (إضافة، تعديل، حذف منطقي، استرجاع). بيفحص المخزن المتأثر، والمكان القديم لو الحركة اتعدّلت أو اتمسحت، والوجهة في التحويل |
| الصرف ≤ المتاح | الصرف بالظبط بالرصيد مسموح، و0.00001 زيادة مرفوضة |
| التزامن | قفل لكل صنف (`pg_advisory_xact_lock`) + قفل الكتابة العام. الفحص بعد الكتابة جوه نفس المعاملة |
| **مفيش تجاوز** | الفحص في القاعدة من غير أي استثناء لدور أو مستخدم، **ومفيش صلاحية «تجاوز» في مصفوفة الصلاحيات** (ومش هتتضاف) |
| تسجيل المرفوض | `audit_log`: `stock.issue_rejected` (رصيد غير كافي) و`stock.movement_rejected` (حركة غير صحيحة)، بالمستخدم والحركة المحاولة والسبب |
| عند عدم الكفاية | الرسالة: «كمّل الاستلام أو اعمل تسوية معتمدة الأول». التسويات المعتمدة: §4 (B-51) |
| شكل الحركة | النوع معروف، والكمية > 0، والصنف موجود، والتحويل لمخزن مختلف |
| مفيش حذف فعلي لحركة | trigger: الحذف منطقي بس عشان الأثر يفضل |
| الحجز نفسه | مايتعدّاش المتاح (trigger على `stock_reservations`) |

**على الواجهة الحالية:**
- المنع موجود أصلًا (`pages-home.js:320`).
- لو الخادم رفض (مثلًا تزامن بين جهازين)، الواجهة بترجّع النسخة الحالية، ورسالتها بقت واضحة: «الرصيد المتاح مايكفيش…» (`web/sync-client.js`).

## 3. فجوات 6.2-ب
- ✅ **حذف صنف عليه حركات:** بقى مرفوض من قاعدة البيانات (`ITEM_HAS_MOVEMENTS`) قبل النقل وبعده. الواجهة الحالية بتعرض «الصنف عليه حركات مخزون — ماينفعش يتمسح»، والصنف من غير حركات بيتمسح عادي.
- **تكلفة المتوسط المتحرك** في الواجهة بتقريب لخانتين (`helpers.js:66`). المعادلة محتاجة اعتماد B-20 قبل نقلها.
- **وظائف الحجز:** إنشاء وفك الحجز محتاجين دورة الشراء والصرف (B-36…B-38).
- **إذن الصرف كمستند بحالات** (مسودة ← معتمد ← مرحّل): حاليًا الحركة نافذة وقت حفظها. التسويات اتعملت كمستند (§4)، والصرف العادي مع 6.2-ب.

## 4. التسويات المخزنية المعتمدة (B-51)
**دورة الحالات:**
```
مسودة/مرتجعة ──إرسال──▶ مُرسلة (محرك الاعتمادات: المستويات من الإعداد) ──آخر اعتماد──▶ معتمدة ──ترحيل آلي (قيد B-50)──▶ مرحّلة
     │                        │ رفض/إرجاع/سحب/إلغاء                                       │ فشل (رصيد مايكفيش) ← بتفضل معتمدة + السبب
     └──إلغاء──▶ ملغاة         ▼                                                          └ إعادة محاولة: صلاحية «ترحيل» المستقلة بس
```

**الأنواع ← الحركة:**

| النوع | الحركة |
|---|---|
| زيادة | `adjust_in` |
| عجز | `adjust_out` |
| تلف أو إعدام | `adjust_out` |
| تصحيح خطأ تسجيل (باتجاه) | `adjust_in` أو `adjust_out` |
| نتيجة جرد (باتجاه) | `adjust_in` أو `adjust_out` |
| تحويل | `transfer` |

**الـ API:**

| الطلب | الوظيفة |
|---|---|
| `GET /api/v1/stock/adjustments` | قائمة التسويات |
| `POST /api/v1/stock/adjustments` | تسوية جديدة |
| `PATCH /api/v1/stock/adjustments/:id` | تعديل (مسودة أو مرتجعة بس) |
| `POST /api/v1/stock/adjustments/:id/submit` | إرسال |
| `POST /api/v1/stock/adjustments/:id/cancel` | إلغاء |
| `POST /api/v1/stock/adjustments/:id/post` | إعادة محاولة الترحيل |

**الاعتماد** من «بانتظار اعتمادي» (`/api/v1/approvals` وشاشة `/app/approvals`).

**الكمية:** نص عشري حتى 5 خانات (B-26).

**التقييم والقيمة:** بعد اعتماد معادلة التكلفة (B-20).

## 5. الجداول والنقل (6.2-ب) — migration `1764600000000-WarehousesCutover` (مابتنقلش بيانات)
**الجداول:**

| الجدول | الأعمدة |
|---|---|
| `wh_locations` | المخازن |
| `wh_items` | الأصناف: كود، اسم، وحدة، تصنيف، `min_qty`، و`avg_cost`/`last_cost` NUMERIC(18,5) زي ما الواجهة بتبعتها |
| `wh_movements` | الحركات: النوع، والكمية NUMERIC(18,5) (B-26)، والمخزن، والوجهة، و`unit_cost`، والمشروع، والفاتورة، و`adjustment_id` |

**الحقول اللي مالهاش عمود** بتتحفظ في `legacy_extra`.

**الـ Adapter:**
- **القراءة:** الـ view `legacy_records` بقى فيه المخازن.
- **الكتابة:** من `/api/sync` بتروح للجداول (`legacy_write_wh_*`) بنفس `rev`.
- **الجرد** (`warehouses.stocktakes`) بيفضل في records. نتيجته بتترحّل كتسوية (B-51).

**B-50 بيتنقل مع البيانات:**
- `wh_balance` بيقرا من المصدر الفعلي (records أو الجداول).
- نفس الفحص على `wh_movements` (قيد)، ومنع الحذف الفعلي.
- **القيود بقت `DEFERRABLE INITIALLY IMMEDIATE`:**
  - **الكتابة العادية:** بتتفحص فورًا زي ما هي.
  - **أمري النقل والرجوع بس:** بيأجّلوا الفحص لنهاية المعاملة على **الحالة النهائية**.
  - **ليه:** حركات اتعدّلت لاحقًا ممكن تبان سالبة مؤقتًا بالترتيب الزمني لوحده، والتجربة بتأكد ده. مفيش تخطّي، والفحص بيحصل قبل الـ commit.

**الأمر:**

| الخطوة | الأمر |
|---|---|
| تجربة | `npm --prefix server run cutover -- warehouses dry-run` |
| تنفيذ | `npm --prefix server run cutover -- warehouses execute --by <الاسم> --backup-log <BACKUP_DIR>/backup-log.jsonl --confirm-backup <وقت النسخة>` |
| رجوع | `npm --prefix server run cutover -- warehouses rollback --by <الاسم> --backup-log ... --confirm-backup ...` |

- نفس شروط 6.1 بالظبط (`PARTIES_MODULE.md §7`).
- خطأ عدم التطابق بيذكر **أسماء الحقول المختلفة** (من غير قيم) للتشخيص.
- **البيانات الحقيقية:** 0 صنف، 0 حركة، مخزن واحد.

## 6. الـ API والشاشة (6.2-ب)
**الـ API:**

| الطلب | الوظيفة |
|---|---|
| `GET /api/v1/warehouses` | الأصناف بأرصدتها، والرصيد والمحجوز لكل مخزن من نفس دالة B-50 |
| `POST /api/v1/warehouses/items` | صنف جديد |
| `PATCH /api/v1/warehouses/items/:id` | تعديل صنف (**التكلفة مش قابلة للكتابة**) |
| `POST /api/v1/warehouses/locations` | مخزن جديد |
| `POST /api/v1/warehouses/transfers` | تحويل بين مخزنين |
| `GET /api/v1/warehouses/movements` | الحركات |

**الشاشة:** `/app/warehouses`، «المخازن» في الواجهة الجديدة، وفيها:
- الأصناف والأرصدة وحد الطلب.
- المخازن.
- **التحويل**: بمنع مسبق بالمتاح + منع قاعدة البيانات.
- الحركات.
- **التسويات**: إنشاء، وإرسال، وإلغاء، وإعادة ترحيل لصاحب «ترحيل».

**الشاشة الكاملة القديمة** (من نفس القائمة) لـ:
- **الاستلام والصرف بتكلفتهم.** الاستلام في الواجهة الحالية بيحسب المتوسط المتحرك، والصرف بيثبّت التكلفة (`helpers.js:66`)، ونقل الحساب ده للخادم = نقل معادلة مالية **قبل اعتمادها (B-20)**.
- الجرد والتقارير.

**ملاحظة B-20/B-51:** حركات التسويات المرحّلة **مالهاش تكلفة وحدة** (مفيش حساب تكلفة على الخادم قبل B-20)، وده هيتكمّل مع اعتماد معادلة التكلفة.
