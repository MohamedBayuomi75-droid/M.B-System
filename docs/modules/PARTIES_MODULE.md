## 3. تصميم الجداول (الخطوة 4) — migration `1764000000000-Parties` (الجداول فاضية)
- `suppliers`:
  - الاسم NOT NULL وغير فاضي.
  - الرقم الضريبي: فاضي أو ≥ 5.
  - `opening_balance NUMERIC(18,4)`.
  - `opening_balance_date date`.
  - `extra_fields jsonb`.
  - `legacy_rev`.
- `customers`:
  - نفس النمط، ومعاه `status` و`code`.
  - `legacy jsonb`: المصفوفات القديمة المتكررة جوه العميل (العقود والمستخلصات وغيرها) بتتحفظ زي ما هي لحد نقل موديولاتها.
- `customer_contacts`: جهات الاتصال بترتيبها.

## 4. الـ API (الخطوة 5)
| الطلب | الوصف |
|---|---|
| `GET /api/v1/suppliers?q=` | قائمة الموردين |
| `GET /api/v1/suppliers/:id` | مورد واحد |
| `POST /api/v1/suppliers` | إضافة مورد |
| `PATCH /api/v1/suppliers/:id` | تعديل مورد (`rev` إلزامي) |
| `GET/POST/PATCH /api/v1/customers` | نفس الشكل للعملاء |
| `GET /api/v1/suppliers/migration-plan` | خطة الترحيل (للمدير بس، قراءة بس) |

- **الكتابة** بتمر بـ `DataService.sync` على نفس السجل اللي الواجهة الحالية بتكتبه. يعني:
  - نسخة واحدة قابلة للكتابة.
  - نفس الصلاحيات ونطاق المشروع.
  - نفس التعارض بـ `rev`: الحقول المحمية بترجّع 409، والنصية آخر واحد يكسب.
  - البث اللحظي وسجل التاريخ شغالين.
- **المبالغ:** بتدخل نصوص عشرية، وبتتخزّن بنفس نوع الواجهة الحالية (رقم JSON). أي قيمة أطول من 15 رقم معنوي بترجّع `PRECISION_LIMIT` بدل ما تتغيّر بصمت.
- **رصيد العميل:** حتى خانتين مؤقتًا، لأن الواجهة الحالية بتقرّبه لخانتين (`core/helpers.js:21 toInt → round2`). القيد ده بيتشال مع نقل شاشة العملاء.
