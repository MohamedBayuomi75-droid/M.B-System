## 2. الوضع المستهدف

نظام ERP داخلي واحد (Web App + PWA) لشركة مقاولات عامة:

- **واجهتان تعملان بالتوازي أثناء الانتقال:** الواجهة الحالية (كما هي) وواجهة Angular + Angular Material. لا تُوقَف أي شاشة قديمة إلا بعد اكتمال بديلتها واختبارها واعتمادها.
- **Backend واحد** (NestJS، Modular Monolith) هو المرجع الوحيد للصلاحيات والتحقق ومنطق العمل.
- **قاعدة بيانات تشغيلية واحدة** (PostgreSQL) تشمل المرفقات.
- **Nginx** كخادم عكسي داخلي بـ HTTPS.
- **وصول داخلي فقط** في المرحلة الأولى.
- **محاسبة قيد مزدوج** مصمَّمة كاملة من البداية ومفعَّلة تدريجيًا (`ACCOUNTING_ROADMAP.md`).
- **محرك اعتمادات متعدد المستويات قابل للتهيئة** (`APPROVAL_WORKFLOW_DESIGN.md`).

## 5. حدود الموديولات (Module Boundaries)

القائمة المعتمدة 23 موديولًا (من `ERP_TARGET_ARCHITECTURE_v1.md §5`).

**قواعد الحدود:**
1. كل موديول يملك جداوله؛ لا يقرأ موديول جداول غيره مباشرة، بل عبر Service معلن للموديول المالك.
2. الربط بين الموديولات بالمعرّفات الثابتة (IDs) فقط — لا ربط بالاسم.
3. الموديولات المالية لا تكتب قيودًا محاسبية مباشرة: تستدعي خدمة «الترحيل» في موديول Accounting بمصدر المستند.
4. أي مستند يحتاج اعتمادًا يمرّ بموديول Approval Workflow؛ لا يحمل كل موديول منطق اعتماد خاصًا به.
5. موديولات **المعدات، العمالة، السلامة والمخاطر، الجودة والاستلام** مستقلة وظيفيًا وإن ارتبطت بالمشروعات (شرط صريح في المعمارية v1).

## 6. Backend واحد وقاعدة بيانات واحدة

### 6.1 واجهتا API فوق نفس الخدمات
| | Compat API (للواجهة الحالية) | Resource API (لـ Angular) |
|---|---|---|
| المسارات | `/api/bootstrap`، `/api/sync`، `/api/changes`، `/api/stream` | `/api/v1/{module}/{resource}` |
| الحالة | **موجودة** (`server/src/data/data.controller.ts`) | **غير موجودة بعد** — تُبنى مع كل موديول |
| الصلاحيات | نفس الـ Guards ونفس قواعد البيانات | نفسها |

### 6.2 قاعدة واحدة بثلاث مجموعات جداول
1. **جداول المنصة** (موجودة): `users, sessions, roles, user_permissions, audit_log, changes, schema_meta, attachments`.
2. **الطبقة الانتقالية JSONB** (موجودة): `records`, `docs` — تخدم الموديولات التي لم تُنقل بعد.
3. **الجداول العلائقية لكل موديول** (غير موجودة): تُنشأ عند نقل كل موديول، بـ PK/FK/UNIQUE/CHECK و`NUMERIC` للأموال.

### 6.3 قاعدة «مصدر حقيقة واحد لكل موديول»
عند نقل موديول إلى جداول علائقية:
- تُرحَّل بياناته من `records` إلى جداوله **مرة واحدة** بعد مطابقة موثّقة (أعداد ومجاميع).
- تصبح الجداول العلائقية هي المصدر الوحيد؛ وتقرأ/تكتب الواجهة الحالية نفس البيانات عبر **Adapter** داخل طبقة التوافق.
- **لا يوجد في أي وقت نسختان قابلتان للكتابة من نفس البيانات.**
- تُحذف الطبقة الانتقالية بعد نقل آخر موديول.

### 6.4 قواعد مالية على مستوى القاعدة (مستهدفة — غير موجودة الآن)
- `NUMERIC` لكل قيمة مالية بـ **4 خانات عشرية وتقريب HALF_UP** (Confirmed — ADR-011)؛ التقريب داخل Backend فقط؛ لا `float` ولا JavaScript `Number` للحساب الدقيق (ADR-023). دقة الكميات والأسعار: مفتوحة (B-26).
- ترقيم المستندات **NO_GAPS** (Confirmed — ADR-013): جدول عدّادات يُقفل صفه ويُزاد داخل معاملة إنشاء المستند (لا تسلسلات `SEQUENCE` لأنها تترك فجوات عند الفشل) + قيد `UNIQUE`؛ لا يُستهلك رقم عند الفشل؛ الملغى يحتفظ برقمه ولا يُحذف أثره (ADR-024). النطاق وشكل الرقم: مفتوح (B-29)؛ الفجوات التاريخية: B-69.
- المستند المرحَّل (`Posted`) غير قابل للتعديل أو الحذف؛ التصحيح بقيد عكسي أو تسوية.
- العمليات المترابطة في Transaction واحدة.

## 7. الانتقال التدريجي إلى Angular

1. **هيكل Angular واحد** تحت `/app/`: مصادقة بنفس الجلسة، حارس صلاحيات يقرأ `/api/me`، مكونات مشتركة (جدول، نموذج، نافذة)، RTL، PWA.
2. **جدول توجيه الصفحات:** لكل صفحة: «قديمة» أو «Angular». قلب صفحة = تغيير سطر، مع إمكانية الرجوع فورًا.
3. **دورة نقل كل موديول:** حصر تفصيلي ← توثيق المعادلات ← تصميم الجداول ← Backend (خدمات + Resource API) ← Adapter للواجهة الحالية ← شاشات Angular ← **اختبارات تطابق** (نفس المدخلات = نفس الأرقام في الواجهتين) ← اعتماد المستخدم ← قلب التوجيه ← إيقاف الشاشة القديمة بعد فترة استقرار.
4. **شرط مسبق لنقل أي موديول:** وجود اختبارات تشغيلية لصفحاته على الواجهة الحالية (27 صفحة من 54 بلا اختبار لعملياتها حاليًا — REPORTED من `FEATURE_INVENTORY.md §1`).
5. **الترتيب المقترح** (قابل للتعديل): المخازن (الأصغر، تجربة للدورة) ← الموردون والفواتير ← العملاء والعقود والمستخلصات ← المشروعات ← الموارد البشرية والعمالة والمعدات ← المستندات ← التقارير والإعدادات.
6. الموديولات الجديدة (المشتريات، السلامة، الجودة، المحاسبة، الخزينة) تُبنى مباشرة في Angular — لا واجهة قديمة لها.

## 9. المرفقات (داخل PostgreSQL — قرار معتمد)

**الوضع الحالي (VERIFIED):** البرنامج الأصلي يحفظ الملفات على القرص ويخزّن المسار الكامل في السجل (`src/main/attachments.js:17-28`)؛ لا صلاحيات على مستوى الملف؛ التحقق من النوع بالامتداد مع خيار «الكل» (`:41-42`). في نسخة الويب المرفقات غير متاحة. في البيانات الحقيقية 111 مرجعًا (109 فاتورة مورد + 2 مورد) والملفات نفسها غير متوفرة هنا.

**التصميم المستهدف:**

| الجدول | المحتوى |
|---|---|
| `attachments` | المعرّف، الكيان المالك (نوع + معرّف)، الاسم الأصلي، النوع، الحجم، **بصمة SHA-256**، رقم الإصدار، الرافع والتاريخ، حالة الفحص، حذف منطقي |
| `attachment_content` | محتوى الملف داخل القاعدة |
| `attachment_versions` (أو عمود إصدار + ربط بالسابق) | تعدد الإصدارات |

- **آلية التخزين داخل PostgreSQL** (اقتراح — ADR-014): محتوى مقسَّم إلى أجزاء `bytea` بحجم ثابت لتمكين الرفع/التنزيل المتدفق دون تحميل الملف كاملًا في الذاكرة، مع بقاء المحتوى ضمن النسخ الاحتياطية وأرشفة WAL تلقائيًا. البديل: Large Objects. الاختيار النهائي بعد قياس على أحجام ملفات الشركة الفعلية.
- **قبل الحفظ:** حد حجم (القيمة: قرار مفتوح)، قائمة أنواع مسموحة، التحقق من توقيع المحتوى لا الامتداد فقط، حساب البصمة.
- **الصلاحيات:** العرض والتنزيل من Backend فقط، بصلاحية المستخدم على **الكيان المالك** (ونطاق مشروعه) — لا روابط مباشرة للملف.
- **الربط:** بالمشروع، العقد، الفاتورة، المورد، العميل، الموظف… بمعرّف الكيان.
- **الترحيل:** مراجع الملفات القديمة تُنقل كبيانات وصفية بحالة «الملف غير متوفر» حتى تُرفع الملفات؛ لا يُحذف أي مرجع.
- **الاستعادة:** اختبار فعلي يقارن عدد المرفقات وبصماتها بعد الاستعادة.

## 11. النشر الداخلي

- خادم Linux داخل الشركة؛ Docker Compose: `nginx` · `server` · `migrate` · `db` (+ خدمة النسخ).
- **Nginx:** TLS، توجيه `/legacy/` و`/app/` (ملفات ثابتة) و`/api/` و`/api/stream` (WebSocket)، حد حجم الطلب، ترويسات الأمان.
- **HTTPS داخلي:** شهادة من مرجع داخلي أو شهادة موثوقة لاسم داخلي — الطريقة: قرار تقني مفتوح مرتبط بتجهيزات الشبكة.
- **Firewall:** 443 من الشبكة الداخلية فقط؛ لا منافذ لقاعدة البيانات؛ لا نشر على الإنترنت؛ لا أنفاق خارجية.
- **بيئات منفصلة:** Development / Testing / Production بقواعد بيانات وأسرار منفصلة.
- **التحديث:** نسخة احتياطية مُتحقق منها ← Migration مُراجَعة ومُجرَّبة على نسخة ← نشر ← فحص صحة ← خطة رجوع (الإصدار السابق + استعادة).
- **حالة الموجود:** Compose بثلاث خدمات (`db → migrate → server`) مجرَّب في بيئة الاختبار (REPORTED)؛ لا Nginx ولا بيئات منفصلة (VERIFIED).

> **قرارات سابقة أُلغيت بقرارات المستخدم النهائية:** Cloudflare Tunnel والوصول من الخارج (D-018)، MinIO للمرفقات (D-018)، Caddy (الخطة القديمة)، PrimeNG (D-017). لا يوجد كود مرتبط بأي منها.
