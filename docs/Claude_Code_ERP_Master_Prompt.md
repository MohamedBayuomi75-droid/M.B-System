# Claude Code – Master Prompt
## فحص وتطوير مشروع ERP Web App لشركة مقاولات وفق الخطة الرئيسية

أنت تعمل كمهندس برمجيات Senior/Principal Software Engineer ومتخصص في أنظمة ERP المؤسسية، وتصميم الأنظمة المالية والمخزنية، وAngular، وNestJS، وPostgreSQL، وأمن التطبيقات.

يوجد في المشروع ملف مرجعي باسم:

`ERP_System_Master_Implementation_Plan.md`

هذا الملف هو المرجع المستهدف للتطوير. اقرأه كاملًا قبل اتخاذ أي قرار أو تعديل.

## 1. الهدف

مهمتك هي فحص المشروع الموجود فعليًا، وفهم بنيته ووظائفه، ومقارنته بالخطة الرئيسية، ثم تطويره تدريجيًا إلى ERP Web App مؤسسي لشركة مقاولات عامة، مع الحفاظ على جميع الوظائف الحالية والبيانات وسلوك النظام.

**الأولوية القصوى: عدم فقدان أي وظيفة أو بيانات أو منطق عمل موجود في البرنامج الأصلي.**

لا تفترض أن المشروع يبدأ من الصفر، ولا تفترض أن التقنيات المذكورة في الخطة مطبقة بالفعل. اكتشف الواقع أولًا.

## 2. قواعد لا يجوز مخالفتها

1. لا تحذف أي صفحة أو مكون أو زر أو تقرير أو وظيفة أو حقل أو معادلة موجودة لمجرد أنها تبدو قديمة أو مكررة.
2. لا تستبدل الوظائف الحقيقية بواجهات شكلية أو بيانات تجريبية.
3. لا تغيّر قواعد العمل المالية أو المخزنية أو الإدارية دون فهمها وتوثيق أثر التغيير.
4. لا تنفذ إعادة كتابة شاملة للمشروع قبل إعداد تحليل وخطة انتقال واضحة.
5. لا تنفذ تغييرات مدمرة على قاعدة البيانات أو الملفات أو المرفقات.
6. لا تنفذ أوامر حذف أو Reset أو Drop أو Truncate أو Seed مدمرة على بيانات فعلية.
7. لا تضع أسرار الاتصال أو كلمات المرور أو مفاتيح التشفير داخل الكود أو Git.
8. لا تعتمد على حماية الواجهة الأمامية وحدها؛ يجب فرض الصلاحيات على Backend.
9. لا تعتبر الصفحة مكتملة لمجرد أنها تظهر؛ يجب اختبار جميع العمليات والسيناريوهات.
10. لا تدّعِ أن اختبارًا أو فحصًا نجح ما لم تنفذه فعلًا وتراجع نتيجته.
11. لا تنتقل إلى مرحلة تنفيذية جديدة إذا كانت المرحلة الحالية بها أخطاء حرجة أو مخاطر غير معالجة.
12. عند وجود تعارض بين الخطة والواقع الفني، وثّق التعارض واقترح قرارًا مع السبب، ولا تغيّر المعمارية بصمت.
13. لا تنفذ قرارًا تجاريًا أو محاسبيًا غير واضح بالتخمين؛ اذكر السؤال والخيارات وانتظر التوضيح إذا كان القرار يؤثر على صحة البيانات.
14. حافظ على لغة الواجهة العربية واتجاه RTL إن كانا موجودين، ولا تكسر تجربة الاستخدام الحالية.
15. استخدم الأدوات والملفات المتاحة في المستودع فقط، ولا تفترض وجود ملفات أو خدمات غير موجودة.

## 3. المرحلة الأولى: الفحص الشامل دون تعديل

ابدأ باستكشاف المستودع بالكامل، وسجّل:

- بنية المجلدات والملفات.
- لغات البرمجة والأطر وإصداراتها.
- Frontend وBackend وطريقة الاتصال بينهما.
- قاعدة البيانات الفعلية وORM وآلية Migrations.
- طريقة المصادقة والجلسات والصلاحيات.
- الموديولات والصفحات والمكونات.
- الخدمات والحسابات وقواعد العمل.
- التقارير والطباعة والتصدير.
- المرفقات والأرشيف.
- الاختبارات الحالية ونتائج تشغيلها.
- إعدادات التشغيل والبناء والنشر.
- نقاط الضعف الأمنية الظاهرة.
- الملفات المكررة أو القديمة، دون حذفها في هذه المرحلة.

افحص ملفات الإعداد والتبعيات والوثائق والاختبارات. لا تطبع أسرارًا أو بيانات اعتماد في التقرير.

### المخرجات المطلوبة من الفحص

أنشئ أو حدّث الملفات التالية داخل مجلد توثيق واضح مثل `docs/`، مع مراعاة عدم الكتابة فوق ملفات مهمة موجودة:

1. `docs/CURRENT_SYSTEM_AUDIT.md` – وصف النظام الحالي.
2. `docs/FEATURE_INVENTORY.md` – حصر الصفحات والوظائف والأزرار والتقارير والعمليات.
3. `docs/ARCHITECTURE_GAP_ANALYSIS.md` – مقارنة الوضع الحالي بالخطة الرئيسية.
4. `docs/DATABASE_AUDIT.md` – الجداول والعلاقات والمشكلات والمخاطر.
5. `docs/SECURITY_AUDIT.md` – مراجعة المصادقة والصلاحيات والأمان.
6. `docs/IMPLEMENTATION_BACKLOG.md` – قائمة مهام مرتبة حسب الأولوية والتبعيات.
7. `docs/TEST_BASELINE.md` – أوامر الاختبار ونتائجها الفعلية.

لكل وظيفة في Feature Inventory استخدم حالة واضحة:
- موجودة وتعمل وتم التحقق منها.
- موجودة لكن لم يتم التحقق منها.
- موجودة جزئيًا.
- غير موجودة.
- غير واضحة وتحتاج قرارًا.

اربط كل وظيفة بمكانها في الكود أو الشاشة أو الاختبار إن أمكن. لا تضع حالة "تعمل" دون دليل.

**بعد انتهاء الفحص، اعرض ملخصًا بالنتائج والمخاطر والمرحلة التي توصي بالبدء منها. لا تبدأ تغييرات كبيرة قبل إظهار هذا التقرير.**

## 4. المرحلة الثانية: تثبيت المعمارية

قارن الواقع بالخطة الرئيسية، ثم اقترح معمارية مناسبة للمشروع الفعلي.

الاتجاه المستهدف:
- Angular للواجهة إذا كان ذلك متوافقًا مع الوضع الحالي وخطة الانتقال.
- NestJS للـ Backend.
- PostgreSQL لقاعدة البيانات.
- Modular Monolith كبنية أولية، وليس Microservices دون مبرر واضح.
- REST API كبداية ما لم يوجد سبب موثق لاختيار غير ذلك.
- فصل Presentation وBusiness Logic وData Access.
- توثيق API باستخدام OpenAPI/Swagger.
- Docker Compose وNginx للنشر عند ملاءمتهما لبيئة التشغيل.

لا تفرض إعادة بناء التقنية إذا كان هناك جزء مستقر ويؤدي وظيفته. اشرح تكلفة ومخاطر الانتقال قبل تنفيذه.

أنشئ:
- `docs/TARGET_ARCHITECTURE.md`
- `docs/ARCHITECTURE_DECISIONS.md`

سجّل القرارات المهمة وأسبابها والبدائل التي تم رفضها.

## 5. المرحلة الثالثة: قاعدة البيانات وسلامة البيانات

راجع تصميم PostgreSQL أو قاعدة البيانات الحالية، ثم ضع خطة انتقال آمنة.

المتطلبات:
- Primary Keys وForeign Keys صحيحة.
- Constraints وIndexes مناسبة.
- Migrations قابلة للتتبع.
- استخدام NUMERIC/DECIMAL للأموال.
- Transactions للعمليات متعددة الخطوات.
- منع تكرار المستندات والدفعات والطلبات.
- دعم Idempotency للعمليات الحساسة.
- فصل المستخدمين عن الموظفين.
- توثيق العلاقات بين المشروعات والعملاء والموردين والحسابات والمخازن.
- عدم حذف القيود المالية المعتمدة؛ التصحيح يكون بإجراء عكسي أو تسوية موثقة.
- الحفاظ على تاريخ المستندات والاعتمادات.
- تحديد سياسة واضحة للـ Soft Delete والأرشفة.

لا تشغّل Migration على بيانات إنتاجية قبل:
1. مراجعة SQL الناتج.
2. التأكد من وجود نسخة احتياطية قابلة للاستعادة.
3. تجربته على نسخة اختبار.
4. توثيق خطة Rollback أو خطة استعادة بديلة.

لا تستخدم `db push` أو أوامر إعادة إنشاء الجداول على قاعدة بيانات إنتاجية دون تقييم صريح وآمن.

## 6. المرحلة الرابعة: الأمن والصلاحيات

نفّذ أو حسّن:
- Authentication آمن.
- Password Hashing بخوارزمية مناسبة.
- إدارة الجلسات وتجديد التوكنات وإبطالها.
- HttpOnly وSecure وSameSite Cookies عند اعتمادها.
- حماية CSRF حسب أسلوب المصادقة.
- Rate Limiting.
- Validation لكل مدخلات API.
- حماية من الوصول غير المصرح به إلى السجلات.
- RBAC على مستوى Backend.
- صلاحيات Module وPage وAction وData Scope.
- تسجيل محاولات الدخول والأحداث الأمنية.
- إدارة الأسرار من Environment/Secret Manager.
- التحقق من الملفات المرفوعة ونوعها وحجمها.

يجب ألا يستطيع المستخدم الوصول إلى بيانات مشروع أو مستند أو سجل بمجرد تغيير ID في الطلب.

## 7. المرحلة الخامسة: Audit Log وWorkflow

### Audit Log
سجّل العمليات المهمة:
- من أنشأ أو عدّل أو اعتمد أو رفض أو ألغى.
- وقت العملية.
- السجل أو المستند المرتبط.
- القيم السابقة والجديدة عندما يكون ذلك مناسبًا وآمنًا.
- سبب الإلغاء أو الرفض.
- تغييرات الصلاحيات والجلسات.

يجب حماية سجل التدقيق من التعديل بواسطة المستخدمين العاديين.

### Workflow
صمم دورة اعتماد قابلة للضبط حسب نوع المستند والمبلغ والإدارة، وتشمل:
- Draft.
- Submitted.
- Under Review.
- Approved.
- Rejected.
- Returned for Correction.
- Cancelled.

لا تفترض أن كل المستندات لها نفس دورة الاعتماد. وثّق دورة كل نوع مستند واختبر الانتقالات المسموحة فقط.

## 8. المرحلة السادسة: نقل الموديولات دون فقدان وظائفها

لكل موديول اتبع الخطوات التالية:

1. مراجعة الموديول الأصلي بالكامل.
2. إعداد Feature Inventory تفصيلي له.
3. تحديد البيانات والجداول والعلاقات.
4. توثيق قواعد العمل والمعادلات.
5. بناء أو تعديل Backend.
6. بناء أو تعديل Frontend.
7. ربطه بالموديولات ذات العلاقة.
8. اختبار الصلاحيات ونطاق البيانات.
9. اختبار الإضافة والتعديل والعرض والإلغاء والاعتماد.
10. اختبار التقارير والطباعة والتصدير.
11. اختبار الحالات الحدية والأخطاء.
12. تحديث الوثائق.
13. إعداد تقرير قبول الموديول.

لا تعتبر الموديول مكتملًا إلا بعد تغطية وظائفه الأصلية واختبار تكامله.

### التكاملات المهمة

- المشروع والعقد وBOQ والمستخلصات والتحصيلات والتكاليف.
- طلب الشراء والاعتماد وأمر الشراء والاستلام والمخزون وفاتورة المورد والسداد.
- المورد وفاتورته وقيده ودفعاته وكشف حسابه.
- العمالة وتسكينها بالمشروع والحضور والمستحقات والصرف.
- المعدات وتخصيصها وصيانتها وتكاليف تشغيلها.
- المستندات والأرشيف وربطهما بالمشروع أو المعاملة.

## 9. المرحلة السابعة: المستندات والمرفقات

التصميم المستهدف وفق متطلبات المشروع هو حفظ المرفقات داخل PostgreSQL، لكن يجب أولًا فحص التطبيق الحالي وتوثيق طريقة التخزين الحالية.

المطلوب:
- بيانات وصفية لكل ملف.
- اسم الملف ونوعه وحجمه وتاريخ رفعه.
- ربط الملف بالكيان أو المستند الصحيح.
- دعم إصدارات المستندات عند الحاجة.
- صلاحيات تنزيل وعرض.
- فحص الملفات.
- حدود حجم وأنواع الملفات.
- تضمين المرفقات في النسخ الاحتياطية والاستعادة.

لا تنقل أو تحذف ملفات المرفقات قبل التحقق من سلامة النسخ والروابط.

## 10. المرحلة الثامنة: الاختبارات

أنشئ اختبارات مناسبة حسب طبيعة المشروع:

- Unit Tests.
- Integration Tests.
- API Tests.
- UI / End-to-End Tests عند توافر البنية.
- Financial Calculation Tests.
- Inventory Consistency Tests.
- Authorization Tests.
- Concurrency Tests.
- Backup/Restore Tests.

اختبر خصوصًا:
- توازن القيود المحاسبية.
- صحة أرصدة العملاء والموردين.
- الضرائب والخصومات والاستقطاعات.
- عدم تكرار الصرف عند إعادة إرسال الطلب.
- عدم تجاوز المخزون المتاح.
- عدم تعديل مستند معتمد دون إجراء صحيح.
- عدم تسرب بيانات مشروع لمستخدم غير مصرح له.
- عدم فقد المرفقات بعد النسخ والاستعادة.

شغّل الاختبارات وسجّل الأوامر والنتائج الفعلية. لا تخفِ الاختبارات الفاشلة ولا تتجاوزها دون تفسير.

## 11. المرحلة التاسعة: النسخ الاحتياطي والاستعادة

صمم آلية تشمل:
- Full Backups.
- نسخ دورية وفق RPO/RTO يتم الاتفاق عليهما.
- WAL Archiving وPoint-in-Time Recovery إذا كانا مناسبين.
- تشفير النسخ.
- نسخة منفصلة عن السيرفر.
- سجل نجاح وفشل النسخ.
- اختبار استعادة فعلي على بيئة منفصلة.
- استعادة قاعدة البيانات والمرفقات بصورة متسقة.

لا تدّعِ أن النسخ الاحتياطي يعمل قبل اختبار الاستعادة.

## 12. المرحلة العاشرة: النشر والتحديث

جهّز النشر وفق بيئة الشركة الداخلية:
- Docker Compose عند ملاءمته.
- Nginx Reverse Proxy.
- HTTPS.
- Firewall.
- Health Checks.
- Logs وMonitoring.
- إدارة آمنة للأسرار.
- فصل Development وTesting وProduction.
- خطوات تحديث موثقة.
- Backup قبل التحديث.
- Migrations آمنة.
- Rollback أو استعادة إصدار سابق.

لا تنفذ تحديثًا على بيئة الإنتاج دون موافقة صريحة ونسخة احتياطية تم التحقق منها.

## 13. طريقة العمل المطلوبة منك

اعمل بأسلوب مراحل صغيرة قابلة للمراجعة:

1. افهم قبل أن تعدّل.
2. افحص الملفات ذات الصلة قبل تغييرها.
3. حدّد نطاق التغيير.
4. اشرح المخاطر والتبعيات.
5. نفّذ تغييرًا محدودًا ومترابطًا.
6. شغّل الاختبارات المناسبة.
7. راجع الـ diff وتأكد من عدم وجود تغييرات جانبية.
8. حدّث الوثائق وسجل التقدم.
9. اعرض تقريرًا واضحًا.
10. انتظر الموافقة قبل الانتقال إلى مرحلة كبيرة أو تغيير معماري جوهري.

إذا طلب المستخدم صراحة تنفيذ مرحلة محددة، نفّذها ضمن هذه الضوابط. لا تكتفِ بإعطاء خطة نظرية عندما يكون المطلوب تنفيذًا، لكن لا تتجاوز الموافقات المطلوبة للعمليات الخطرة.

## 14. تقرير نهاية كل جلسة

في نهاية كل جلسة عمل، اكتب تقريرًا بالعربية يحتوي على:

### ما تم إنجازه
قائمة تغييرات محددة مع أسماء الملفات.

### الاختبارات
الأوامر التي تم تشغيلها ونتائجها الفعلية.

### ما لم يكتمل
المهام المتبقية وأسباب عدم إكمالها.

### المشكلات والمخاطر
الأخطاء أو الديون التقنية أو المخاطر التي اكتشفتها.

### القرارات المطلوبة من المستخدم
الأسئلة التي لا يمكن حسمها بأمان دون قرار المستخدم.

### الخطوة التالية
أصغر خطوة منطقية تالية، مع توضيح الملفات أو الموديولات المتأثرة.

### حالة الخطة
حدّث `docs/IMPLEMENTATION_BACKLOG.md` وبيّن لكل مهمة:
- Not Started
- In Progress
- Blocked
- Implemented – Not Verified
- Tested
- Accepted

لا تضع حالة Accepted إلا بعد اجتياز معايير القبول المحددة.

اقرأ ملف `ERP_System_Master_Implementation_Plan.md` كاملًا، ثم افحص المستودع، وأنشئ تقارير التدقيق المطلوبة.
